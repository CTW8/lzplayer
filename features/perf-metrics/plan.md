# perf-metrics 实施计划（播放器性能指标采集与可视化）

> 设计文档: ../../docs/test-console-ui-design.md
> **设计见 docs/test-console-ui-design.md 第 3.C / 3.F / 5 节**（本 feature 未新建设计文档：
> 按用户要求"先在原来设计稿上修改"，方案已于 2026-08-08 直接修订进 test-console-ui 设计稿）
> 创建日期: 2026-08-08

## 方案摘要

原测试台只有八项瞬时读数，能说明"慢"但说明不了"慢在哪一段"。本 feature 补齐一整套
可复现的性能测量手段：native 侧统一 steady_clock 打点，采集启播里程碑 T0~T8、
稳态三项（解码耗时/上屏耗时/同步余量）与 seek 三阶段；直方图在 native 侧累积、
只回传 p50/p95/max；Java 侧读 /proc 补资源指标。UI 上原「诊断面板」升级为六分页
「性能面板」（概览/启播/Seek/稳态/资源/日志，含启播瀑布图与火花线），主控台加可开关
的三行「性能 HUD」，另加一键「基准序列」跑分（固定 6 步约 60s，产出 txt + json 双份
带环境指纹的报告）。

设计稿本次修订涉及：头部修订说明、3.A.3 性能 HUD、3.C 性能面板六分页、3.F 基准序列、
第 5 节指标目录与采集点、第 6 节验收标准追加 7 条、第 7 节风险追加 6 条。

## 实施步骤

1. **步骤1 native 时间基准与启播里程碑**
   - 全部时间戳统一 `std::chrono::steady_clock`；Java 侧传入的调用时刻只作为 T0 参数下传，
     不与 native 时钟相减。
   - 在 T0~T8 九个采集点打点，位置严格按设计 5.2 表：T0 `VEPlayer::onPrepare` 入口、
     T1 `VEDemux::openInput` 返回后、T2 `avformat_find_stream_info` 返回后、
     T3 `VEDemux::buildTrackList` 返回后、T4 `VEPlayer::continuePrepare` 返回前、
     **T4a 硬解 `VEMediaCodecVideoDecoder::configureCodec` 末尾与软解 `VEVideoDecoder::prepare`
     末尾两处分别打点**、T5 `VEPlayer::onStart` 入口、T6 视频解码器首个 `VEFrame` 处、
     T7 既有 `FIRST_FRAME` 上报点、T8 `VEAudioRender::anchorClock` 首次调用处。
   - 新增 `VEPlayer::getStartupTraceJson()`（独立 getter，不塞进 stats）。
   - 验收：九个点全部有值；派生量（打开 T2−T0 / 建链 T4−T3 / 首帧 T7−T5 / 首声 T8−T5 /
     总耗时 T7−T0）自洽；各段之和与总耗时误差 < 5ms；无负值。

2. **步骤2 native 稳态指标**
   - 新增打点：解码耗时、上屏耗时、同步余量（`VEAVsync` 等待时已算出该差值，只需留存）。
   - **软解与硬解的「解码耗时」不是同一件事，必须分成两个字段**（实施时纠偏，见下方"口径纠偏"）：
     `videoDecodeMs` 只由软解填（`avcodec_send/receive` 的单帧 CPU 成本）；
     `codecLatencyMs` 只由硬解填（pts→出队的端到端延迟，**含背压等待，不是解码耗时**）。
   - 固定桶宽直方图在 **native 侧**累积，跨 JNI **只回传 p50/p95/max + 样本数**，不回传原始样本。
   - 队列水位峰值记录（当前值已有 `getQueueDepth`）。
   - 扩展 `getStatsJson()` 输出上述字段；**不新增回调通道**，沿用既有拉模式。
   - 验收：分位数在播放中有合理数值；样本 < 30 时明确回传"样本不足"标记（-1）；
     打点开启前后帧率无可测退化 —— **判定方式（原「两次跑差异 < 15%」已被实测证伪，改为）**：
     N ≥ 3 次取中位数；只对**确定性段（打开 / 解析 / 建链）**做严格比对；
     首帧解码与首帧上屏两段单独看分布，不设百分比阈值（软解总耗时仅约 12ms，
     单次首帧调度抖动即可超过 15%）。

3. **步骤3 seek 追踪**
   - 记录三阶段耗时（PAUSING / SEEKING / PRIMING）+ seek 后首帧耗时 +
     精度（首帧实际 pts − 请求位置）。
   - 新增 `VEPlayer::getSeekTraceJson()`，保留**最近 10 次**（环形缓冲）。
   - **本步骤需先造出触发 seek 的手段**（seek 的 intent extra 或 UI 自动化路径）——
     步骤2 遗留的「seek 后队列峰值归零」验收因缺此手段未验，本步骤一并验掉。
   - 验收：连续 seek 10 次以上，列表只保留最近 10 条且顺序正确；
     精度列在已知素材上与 ffprobe 的关键帧位置对得上；
     **seek 后队列峰值归零**（步骤2 遗留项）。

4. **步骤4 Java 层数据模型 —— 已重新定位为「后续重构」，不再是步骤5 的前置**
   > **2026-08-08 顺序调整**：步骤5 已提前实施并跳过本步骤。面板直接用 `org.json.JSONObject`
   > 读原始 JSON，没有等中间层。理由见 status.md「计划外的顺序调整」。
   - 内容改为：**把性能面板里的内联 JSON 解析抽成扩展类** —— `StartupTrace` / `SeekTrace` /
     `PlayerStats` 扩字段（稳态分位数、队列峰值等），面板改为消费这些类而非直接解析。
   - 资源指标已在步骤5 中随面板落地（纯 Java 侧、无 native 改动）：进程 CPU（`/proc/self/stat`
     utime+stime 差分）、线程 CPU（`/proc/self/task/<tid>/stat`，线程名取 `comm`）、
     RSS（`/proc/self/statm`）、native heap（`Debug.getNativeHeapAllocatedSize()`），
     CPU% 同时给单核归一值与整机占比。本步骤只负责把它们从面板里搬进数据类。
   - 触发时机：**当第二处消费方出现时**（步骤7 跑分报告也要解析同样的 JSON），
     此前内联解析可接受，不必为单一消费方提前造中间层。
   - 验收：解析类对畸形/缺字段 JSON 不崩；面板行为与重构前逐页一致（截图比对）；
     线程 CPU 之和 ≤ 进程 CPU；线程名与 native `ALooper::setName()` 一一对应。

5. **步骤5 性能面板 UI**（Kotlin，改既有 `DiagnosticsSheet.kt`）
   - 全高 BottomSheet（expanded 态）+ 顶部六分页 tab（概览/启播/Seek/稳态/资源/日志），
     tab 间 SMPTE 彩条细条；标题栏 [跑分] [导出]。
   - 概览页四个大字读数 + 原八项紧凑栅格 + 三个策略开关（强制软解 / 强制 OpenSL ES /
     Vulkan 渲染，后者注明需同时强制软解）；渲染后端名用已实现的
     `VEVideoDisplay::renderBackendName()`。
   - 新增控件：启播瀑布图、火花线、分位数表。曲线用固定长度环形缓冲；
     **只有可见页刷新，切页才重绘**。
   - **刷新节拍（实施时纠偏）**：面板**自带 1 秒 ticker**，`setOnShowListener` 起、
     `setOnDismissListener` 停，只在面板显示期间运行。原写"搭进度 tick，不另开定时器"不成立——
     CPU 占用需两次采样求差，而暂停/播完后进度回调停发，会让 CPU 永远停在"首次采样"。
     设计稿 3.A.3 已收窄适用范围：**HUD 搭进度 tick，面板自有节拍**。
   - **面板文案一律纯文本**：`TextView` 不解析 Markdown，文案里不得出现 `**强调**`，
     星号会原样显示。
   - **未接通的页不留空白**：数据源未就绪的页必须明写"尚未接通（步骤N）"并列出接通后
     会显示什么，否则会被当成功能坏了。
   - **清理步骤1/2 的临时脚手架**：`ConsoleActivity.dumpStartupTrace()` 目前在每个进度 tick
     覆盖写 `filesDir/perf/last-startup.json` 与 `last-stats.json`（为绕开设备 logcat 配额），
     面板做好后改为面板按需拉取，删掉每 tick 写文件的逻辑。
   - 验收：六页均有真实数据；瀑布图能高亮最大项（人为插 200ms 延时可验证）；
     样本不足处显示 `--`；面板打开后主线程无掉帧；每 tick 写文件的脚手架已删除。

6. **步骤6 性能 HUD**
   - 主控台左下角三行等宽小字（帧率/丢帧、A/V/缓冲、CPU/首帧），默认关闭，
     四宫格入口旁小开关切换；横屏沉浸态下与原 HUD 一同常驻；刷新搭既有进度 tick。
   - 验收：开关即时生效；灰度截图下可判读；关闭状态下不产生任何采样开销。

7. **步骤7 基准序列（一键跑分）**
   - 6 步自动序列（冷启动起播 / 稳态 15s / 5 个百分比位置 seek / 三档变速各 5s /
     音轨与字幕切换 / seek 至末尾播到 EOS），位置用**百分比**不用绝对秒数，
     步间插 1s 静默，期间禁用其它交互并显示进度与剩余时间、允许中断。
   - 报告落 `/sdcard/Android/data/<pkg>/files/perf/<时间戳>-<素材名>.{txt,json}`，
     两份**同源**；头部环境指纹：机型、Android 版本、素材（分辨率/编码/帧率/时长）、
     三个策略开关状态、渲染后端、音频后端。硬解/软解首帧不可比的脚注写进报告。
   - 中断产出的报告标记「不完整」，不得用于对照。
   - 验收：txt 与 json 内容一致；指纹完整；同素材同配置**跑 N ≥ 3 次取中位数**，
     确定性段（打开/解析/建链）严格比对，首帧两段单独看分布。
     **原「连续跑两次差异 < 15%」判定已废**——步骤2 实测软解启播 21.3 / 12.4 / 11.7ms，
     绝对值太小，单次调度抖动就能破 15%。

8. **步骤8 真机验证**
   - 逐条对照设计第 6 节 12 条验收标准（原 5 条 + 性能面板追加 7 条）。
   - 重点核对：同步余量 p95 正常播放 > 0，且加压后**先看到余量下降、再看到丢帧出现**
     （顺序颠倒则该指标失去预警意义）；线程 CPU 之和 ≤ 进程 CPU 且线程名可对应。
   - 报告落 `test-reports/`。
   - 验收：12 条逐条有结论；发现的 native 缺陷归入对应 feature，不在本 feature 混改。

## 关键约束（实施时最容易违反，必须遵守）

1. **测量不能影响被测对象**：每帧打点只做 `steady_clock` 取值与直方图累加，
   **不做字符串格式化、不跨 JNI 传原始样本**（60fps 一分钟就是 3600 条）。
   CPU 采样只在面板打开或跑分期间进行。
2. **首帧必须拆成两段**：T5→T6（解码出首帧）与 T6→T7（等同步时钟）分开展示。
   两段优化方向相反——前者要加快解码，后者说明画面已就绪只是在等时钟、
   该动起播锚点策略。合成一个数字会把人引向错误方向
   （先前"起播 0.6s 追平"议题就踩过这个坑）。
3. **硬解与软解的首帧耗时不可直接互比**：T7 的物理含义不同
   （软解 = 提交 GLES/Vulkan 并 swap，硬解 = 交给 SurfaceFlinger），报告里必须有脚注。
   **推广（步骤2 口径纠偏后新增）：口径不同的量绝不能共用字段名。** 同名字段是最隐蔽的
   不可比形态——脚注还有人看，字段名一样则看的人根本不会察觉。凡两条路径含义不同的量，
   一律拆成两个字段、各自只表达一件事，另一条路径留 n=0 → -1 → 上层显示 `--`。
   已按此处理：`videoDecodeMs`（软解，单帧解码 CPU 成本）与 `codecLatencyMs`
   （硬解，codec 端到端延迟，含背压等待）。
4. **禁止 wall clock**：会被系统时间调整/NTP 校准打乱产出负耗时。
   跨语言段以 native 记录为准，不要两个时钟源相减。
5. **样本不足时显示 `--`**：分位数样本 < 30 条时不得给出数字。
6. **跑分报告必须带环境指纹**（机型 / Android 版本 / 素材参数 / 三个策略开关 /
   渲染后端 / 音频后端），缺指纹的报告不能用于对照；中断产出的报告标记「不完整」。
7. **同步余量是丢帧前兆指标**：验收时要确认"余量先下降、丢帧后出现"的顺序，
   顺序颠倒则该指标失去意义。
8. **不新增回调通道**：数值快照走既有拉模式（`getStatsJson` 扩展 +
   `getStartupTraceJson` / `getSeekTraceJson` 两个独立 getter），
   不塞进 `Native → NativeLib.EventHandler → IVEPlayerListener` 事件流。
9. **步骤顺序必须让用户看得见进展（2026-08-08 新增）**：不要把所有可见产出排在末尾。
   有 UI 的 feature，UI 一旦有一路真实数据可展示就先做，**中间层等第二个消费方出现再抽**。
   本 feature 原顺序（四步 native 后才做面板）已被用户反馈证明不可取。

## 依赖与顺序

- 步骤1/2/3 是 native 侧，互相独立可并行。
- **2026-08-08 调整**：步骤5 **不再依赖步骤4**。原顺序把 UI 排在四个 native 步骤之后，
  导致做完步骤1/2 界面上完全看不到变化（只有 JSON 文件），用户批了设计稿却看不到结果。
  现改为：**只要有一路数据可展示就先把 UI 做出来**，中间层留到有第二个消费方时再抽
  （步骤4 已重定位为后续重构）。步骤5 已完成主体，步骤3 的 Seek 页在 native 打点接通后补。
- 步骤6 可与步骤5 并行（同一批 UI 文件）；步骤7 依赖 5；步骤8 依赖全部。
- **依赖 test-console-ui**：性能面板是在它的诊断面板上改的。
- **与 vulkan-renderer 有交集**：资源页/概览页要显示渲染后端名，
  `VEVideoDisplay::renderBackendName()` 已实现可直接用。
- **与 high-perf-player 的关系**：本 feature 建成后，high-perf-player 的性能类验收指标
  （起播耗时、seek 耗时、CPU 占用）才第一次有了可复现的测量手段。
- **与 no-audio-audioonly 遗留项的关系**：该 feature 遗留的「起播约 0.6s 追平」与
  音频侧「首秒静音」，本 feature 的启播瀑布图（尤其 T5→T6 / T6→T7 拆分与 T8 首声）
  正是定位它们的工具。

## 风险

1. **与 test-console-ui 未收口的改动冲突（最高优先）**：test-console-ui 步骤8 自测尚未完成、
   改动仍在工作区，两者会碰 `DiagnosticsSheet.kt` 与 `ConsoleActivity.kt`。
   **原建议：先把 test-console-ui 收口再动本 feature 的步骤 5/6。**
   > **2026-08-08 更新：该建议未采纳** —— 用户反馈"做完两步界面看不到变化"，步骤5 已提前实施，
   > `DiagnosticsSheet.kt` 与 `ConsoleActivity.kt` 均已改动（后者新增
   > `statsJsonProvider` / `startupTraceProvider` 两个构造参数）。
   > 风险转化为：**test-console-ui 步骤8 自测必须以这两个文件的当前形态为准**，
   > 不能按其原设计去核对。
2. **测量开销反向污染结论**：见关键约束 1；若打点后 CPU 指标本身抬升，
   所有对照数据失效。步骤2 验收必须包含"打点前后无可测退化"。
3. **T4a 双路径漏打点**：硬解与软解 configure 在两个类里，只改一处会导致某条路径缺段，
   进而"各段之和 = 总耗时"校验失败。
4. **硬解链路 T6/T7 语义模糊**：MediaCodec 直出 Surface 时"解出首帧"与"上屏"边界不如软解清晰，
   需实测确认打点位置，必要时在报告中标注该路径的口径。
5. **seek 精度依赖素材关键帧分布**：验收需固定素材并事先用 ffprobe 取关键帧位置作基准。
6. **跑分序列 60s 期间的外部干扰**：系统后台任务、温控降频会造成跑次间抖动；
   **不要用「两次差异 < 15%」作判定**（步骤2 已证伪，软解绝对值仅约 12ms）：
   N ≥ 3 次取中位数，确定性段严格比对，首帧两段看分布。
7. **面板数据量大拖卡主线程**：六页 + 曲线，需固定长度环形缓冲 + 只刷可见页。
8. **native bug 归属**：本 feature 只负责暴露与可视化，测量中暴露的播放核心缺陷
   归到对应 feature（high-perf-player / vulkan-renderer 等）修，不在本 feature 混改。
