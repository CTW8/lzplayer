> 设计文档: ../../docs/test-console-ui-design.md

> 创建日期: 2026-08-08

## 方案摘要

原测试台只有八项瞬时读数，能说明"慢"但说明不了"慢在哪一段"。本 feature 补齐一整套
可复现的性能测量手段：native 侧统一 steady_clock 打点，采集启播里程碑 T0~T8、
稳态三项（解码耗时/上屏耗时/同步余量）与 seek 三阶段；直方图在 native 侧累积、
只回传 p50/p95/max；Java 侧读 /proc 补资源指标。UI 上原「诊断面板」升级为六分页
「性能面板」（概览/启播/Seek/稳态/资源/日志，含启播瀑布图与火花线），主控台加可开关
的三行「性能 HUD」，另加一键「基准序列」跑分（固定 6 步约 60s，产出 txt + json 双份
带环境指纹的报告）。

设计稿 2026-08-08 修订涉及：头部修订说明、3.A.3 性能 HUD、3.C 性能面板六分页、3.F 基准序列、
第 5 节指标目录与采集点、第 6 节验收标准追加 7 条、第 7 节风险追加 6 条。

设计稿 **2026-08-09 修订**：3.C 新增「面板读数三态」硬性规定；C4 新增「丢帧构成 · 按原因分类」
区块与四类语义；5.3 增补四个丢帧分类计数的定义与采集点；第 6 节追加 3 条验收；
**新增第 8 节「指标体系评审结论」**（按环节缺口 + 三梯队 + 两条准入门槛 +
结构性缺口「只有聚合快照、没有时间线」）—— 对应本 plan 新增的**步骤9**与关键约束 10~13。

## 实施步骤

1. **步骤1 native 时间基准与启播里程碑**
   - 全部时间戳统一 `std::chrono::steady_clock`；Java 侧传入的调用时刻只作为 T0 参数下传，
     不与 native 时钟相减。
   - 在 T0~T8 九个采集点打点，位置严格按设计 5.2 表：T0 `VEPlayer::onPrepare` 入口、
     T1 `VEDemux::openInput` 返回后、T2 `avformat_find_stream_info` 返回后、
     T3 `VEDemux::buildTrackList` 返回后、T4 `VEPlayer::continuePrepare` 返回前、
     **T4a 硬解 `VEMediaCodecVideoDecoder::configureCodec` 末尾与软解 `VEVideoDecoder::prepare`
     末尾两处分别打点**、T5 `VEPlayer::onStart` 入口、T6 视频解码器首个 `VEFrame` 处、
     T7 既有 `FIRST_FRAME` 上报点、T8 `VEAudioRender::anchorClock` 首次调用处。
   - 新增 `VEPlayer::getStartupTraceJson()`（独立 getter，不塞进 stats）。
   - 验收：九个点全部有值；派生量（打开 T2−T0 / 建链 T4−T3 / 首帧 T7−T5 / 首声 T8−T5 /
     总耗时 T7−T0）自洽；各段之和与总耗时误差 < 5ms；无负值。

2. **步骤2 native 稳态指标**
   - 新增打点：解码耗时、上屏耗时、同步余量（`VEAVsync` 等待时已算出该差值，只需留存）。
   - **软解与硬解的「解码耗时」不是同一件事，必须分成两个字段**（实施时纠偏，见下方"口径纠偏"）：
     `videoDecodeMs` 只由软解填（`avcodec_send/receive` 的单帧 CPU 成本）；
     `codecLatencyMs` 只由硬解填（pts→出队的端到端延迟，**含背压等待，不是解码耗时**）。
   - 固定桶宽直方图在 **native 侧**累积，跨 JNI **只回传 p50/p95/max + 样本数**，不回传原始样本。
   - 队列水位峰值记录（当前值已有 `getQueueDepth`）。
   - 扩展 `getStatsJson()` 输出上述字段；**不新增回调通道**，沿用既有拉模式。
   - 验收：分位数在播放中有合理数值；样本 < 30 时明确回传"样本不足"标记（-1）；
     打点开启前后帧率无可测退化 —— **判定方式（原「两次跑差异 < 15%」已被实测证伪，改为）**：
     N ≥ 3 次取中位数；只对**确定性段（打开 / 解析 / 建链）**做严格比对；
     首帧解码与首帧上屏两段单独看分布，不设百分比阈值（软解总耗时仅约 12ms，
     单次首帧调度抖动即可超过 15%）。

3. **步骤3 seek 追踪**
   - 记录三阶段耗时（PAUSING / SEEKING / PRIMING）+ seek 后首帧耗时 +
     精度（首帧实际 pts − 请求位置）。
   - 新增 `VEPlayer::getSeekTraceJson()`，保留**最近 10 次**（环形缓冲）。
   - **本步骤需先造出触发 seek 的手段**（seek 的 intent extra 或 UI 自动化路径）——
     步骤2 遗留的「seek 后队列峰值归零」验收因缺此手段未验，本步骤一并验掉。
   - 验收：连续 seek 10 次以上，列表只保留最近 10 条且顺序正确；
     精度列在已知素材上与 ffprobe 的关键帧位置对得上；
     **seek 后队列峰值归零**（步骤2 遗留项）。

4. **步骤4 Java 层数据模型 —— 已重新定位为「后续重构」，不再是步骤5 的前置**
   > **2026-08-08 顺序调整**：步骤5 已提前实施并跳过本步骤。面板直接用 `org.json.JSONObject`
   > 读原始 JSON，没有等中间层。理由见 status.md「计划外的顺序调整」。
   - 内容改为：**把性能面板里的内联 JSON 解析抽成扩展类** —— `StartupTrace` / `SeekTrace` /
     `PlayerStats` 扩字段（稳态分位数、队列峰值等），面板改为消费这些类而非直接解析。
   - 资源指标已在步骤5 中随面板落地（纯 Java 侧、无 native 改动）：进程 CPU（`/proc/self/stat`
     utime+stime 差分）、线程 CPU（`/proc/self/task/<tid>/stat`，线程名取 `comm`）、
     RSS（`/proc/self/statm`）、native heap（`Debug.getNativeHeapAllocatedSize()`），
     CPU% 同时给单核归一值与整机占比。本步骤只负责把它们从面板里搬进数据类。
   - 触发时机：**当第二处消费方出现时**（步骤7 跑分报告也要解析同样的 JSON），
     此前内联解析可接受，不必为单一消费方提前造中间层。
   - 验收：解析类对畸形/缺字段 JSON 不崩；面板行为与重构前逐页一致（截图比对）；
     线程 CPU 之和 ≤ 进程 CPU；线程名与 native `ALooper::setName()` 一一对应。

5. **步骤5 性能面板 UI**（Kotlin，改既有 `DiagnosticsSheet.kt`）
   - 全高 BottomSheet（expanded 态）+ 顶部六分页 tab（概览/启播/Seek/稳态/资源/日志），
     tab 间 SMPTE 彩条细条；标题栏 [跑分] [导出]。
   - 概览页四个大字读数 + 原八项紧凑栅格 + 三个策略开关（强制软解 / 强制 OpenSL ES /
     Vulkan 渲染，后者注明需同时强制软解）；渲染后端名用已实现的
     `VEVideoDisplay::renderBackendName()`。
   - 新增控件：启播瀑布图、火花线、分位数表。曲线用固定长度环形缓冲；
     **只有可见页刷新，切页才重绘**。
   - **刷新节拍（实施时纠偏）**：面板**自带 1 秒 ticker**，`setOnShowListener` 起、
     `setOnDismissListener` 停，只在面板显示期间运行。原写"搭进度 tick，不另开定时器"不成立——
     CPU 占用需两次采样求差，而暂停/播完后进度回调停发，会让 CPU 永远停在"首次采样"。
     设计稿 3.A.3 已收窄适用范围：**HUD 搭进度 tick，面板自有节拍**。
   - **面板文案一律纯文本**：`TextView` 不解析 Markdown，文案里不得出现 `**强调**`，
     星号会原样显示。
   - **读数一律走三态（2026-08-09 补做，原先欠账）**：`null` → `--`；负数**原样显示 + 标红 +
     注明"← 负值：采集点顺序颠倒"**；正常值正常显示。判定基于 `isNull()`（`msOrNull()` 辅助），
     **禁止 `optDouble(key, -1.0)` 这类默认值兜底**（详见关键约束 10）。
     启播页分段同样不得静默丢弃负值。
   - **稳态页「丢帧构成 · 按原因分类」区块（2026-08-09 新增，已完成）**：四行
     late / overflow / stale / seekCatchup，每行带语义说明；late 与 overflow 非零标警告/危险色，
     stale 与 seekCatchup 用弱化色并注明"正常 / 非缺陷"。
   - **未接通的页不留空白**：数据源未就绪的页必须明写"尚未接通（步骤N）"并列出接通后
     会显示什么，否则会被当成功能坏了。
   - **清理步骤1/2 的临时脚手架**：`ConsoleActivity.dumpStartupTrace()` 目前在每个进度 tick
     覆盖写 `filesDir/perf/last-startup.json` 与 `last-stats.json`（为绕开设备 logcat 配额），
     面板做好后改为面板按需拉取，删掉每 tick 写文件的逻辑。
   - 验收：六页均有真实数据；瀑布图能高亮最大项（人为插 200ms 延时可验证）；
     样本不足处显示 `--`；面板打开后主线程无掉帧；每 tick 写文件的脚手架已删除。

6. **步骤6 性能 HUD** —— **Done（2026-08-16）**
   - 主控台左下角三行等宽小字（帧率/丢帧、A/V/缓冲、CPU/首帧），默认关闭，
     四宫格入口旁小开关切换；横屏沉浸态下与原 HUD 一同常驻；刷新搭既有进度 tick。
   - 验收：开关即时生效；灰度截图下可判读；关闭状态下不产生任何采样开销。
   - **2026-08-16 关闭判定：交付物存在且在运行**（`ConsoleActivity.kt:113` 定义 `landHud`、
     `:167` onCreate 调 `buildLandscapeHud()`、`:458` 实现）。
   - **与 console-ui-v2 八格仪表带是分工，不是被它取代** —— 竖屏用八格仪表带
     （同文件 24 处 `gauge` 引用），横屏用本步骤的紧凑 HUD，
     理由已写在代码注释里：**横屏要满画面核对画幅/色彩/旋转，八格仪表带会挡住画面**。
     **两者都要保留，后续 review 不得当重复功能删掉。**

7. **步骤7 基准序列（跑分报告）** —— **2026-08-15 重新拆分为 7a~7f，形态由「面板里的一键跑分按钮」
   改为「intent 驱动 + 宿主机生成报告」，理由见下方「7 形态变更」**

   > 原始定义保留：6 步自动序列（冷启动起播 / 稳态 15s / 5 个百分比位置 seek / 三档变速各 5s /
   > 音轨与字幕切换 / seek 至末尾播到 EOS），位置用**百分比**不用绝对秒数，步间插 1s 静默；
   > 报告落 `<pkg>/files/perf/<时间戳>-<素材名>.{txt,json}`，两份**同源**；头部环境指纹：
   > 机型、Android 版本、素材（分辨率/编码/帧率/时长）、三个策略开关、渲染后端、音频后端；
   > 硬解/软解首帧不可比的脚注写进报告；中断产出的报告标记「不完整」，不得用于对照。

   **7 形态变更（2026-08-15）**：
   - **逐秒时间线的唯一来源是 logcat**（VESTAT / VERENDER / VEGAUGE，由
     observability-instrumentation 交付）。让 app 读自己的 logcat 再写进报告，既脆弱、
     又让"测量本身"进入被测进程（违反关键约束 1）。宿主机侧天然有这条流。
   - decoder-test-redesign §5.1 已确定**一切经 intent 驱动**，§5.2 明确"复用跑分报告格式"。
     两边共用一套 harness，跑分是它的第一个用例；做成面板按钮则解码测试要另造一套。
   - 素材指纹要 ffprobe（分辨率/编码/帧率/码率/时长/有无音轨），宿主机现成，app 侧要另写一套。
   - `ConsoleActivity.kt` / `DiagnosticsSheet.kt` 正被 console-ui-v2 大改，面板按钮会直接撞车。
   - **副作用（重要）**：报告生成方在宿主机而非 Kotlin，**步骤4「抽 JSON 解析类」的触发条件
     （第二个 Kotlin 消费方出现）因此不成立，步骤4 继续挂起**。

   - **7a intent 参数补齐**（对应 decoder-test-redesign §5.1 中不含故障注入的那部分）
     - 新增 `--es seekPercents 10,50,90,0,75` / `--ei playSeconds 15` / `--es caseName <名>`。
       故障注入三个参数（`faultHwCreate` / `faultHwConfigure` / `faultHwAfterFrames`）
       **不在本步骤**，归 decoder-test-redesign。
     - `seekPercents` 用百分比、按序执行、每次之间固定间隔；`playSeconds` 到点自动收尾
       （停止并触发 7b 的落盘），使一条命令能跑完不需要点屏幕。
     - 验收：单条 `am start` 命令可完成「起播 → 稳态 N 秒 → 按序 seek → 收尾落盘」全程；
       不带这些参数时行为与现在**完全一致**（回归现有手工路径）；
       参数非法（百分比越界/非数字）时**明确拒绝并记进报告**，不静默忽略。

   - **7b 收尾时的一次性快照落盘**
     - 序列结束时写**一份**聚合 JSON（`getStatsJsonRaw` + `getStartupTrace` + `getSeekTraceJson`
       + 三个策略开关 + 渲染/音频后端 + caseName + 是否完整），文件名带时间戳与 caseName。
     - **必须写临时文件再 rename**：步骤5 清掉的那套脚手架用 `writeText` 先截断再写，
       被 adb 读到中间态就是空文件，已误导过一次（commit 77add60）。
     - **只在收尾写一次**，不得恢复"每 tick 写文件"。
     - 验收：`adb shell run-as ... cat` 在任意时刻读到的要么是上一份完整文件、要么无文件，
       不存在空文件或半截 JSON；中断（未播够 `playSeconds` 即退出）时文件里
       `complete=false`。

   - **7c 宿主机 harness 脚本**（`scripts/run-benchmark.sh`，与 `gen-test-assets.sh` 并列）
     - 一次运行 = 清 logcat → `am start` 带 7a 参数 → 抓 `VESTAT|VERENDER|VEGAUGE` 到文件 →
       等待收尾 → 拉回 7b 快照 → `ffprobe` 取素材指纹 → 调 7d 生成报告。
     - **必须检测 logcat 行丢失**：VESTAT 的 `t=` 是连续秒序号，缺号即被 300 行配额丢弃。
       60s 序列约 5 行/秒（VESTAT 1 + VERENDER 1 + VEGAUGE 3）**已逼近该机 300 行配额**，
       这是本步骤最现实的风险，必须先量后做。
     - 验收：同一命令在同一素材上跑两次得到两份结构相同的报告；`t=` 缺号时报告头部
       标「时间线不完整」并给出缺失秒号，**不得当作正常报告用于对照**。

   - **7d 报告生成器（txt + json 同源）**
     - 三段结构，严格按 decoder-test-redesign §5.2：
       ① **环境指纹**（机型 / Android 版本 / 素材全参数 / 三个策略开关 / 渲染后端 /
       音频后端 / 构建开关 `VE_QUIET_LOG`、`VE_TRACE_FRAME` / 注入状态占位）；
       ② **判据逐条 PASS/FAIL**，每条同时打印**实测值与交叉校验值**（判据表见
       decoder-test-redesign §4，七条）；
       ③ **逐秒时间线**（VESTAT 全列 + VERENDER + VEGAUGE 覆盖率）。
     - **txt 与 json 必须由同一份中间数据结构渲染**，不得各算一遍。
     - **每列必须附采样时刻说明**（2026-08-15 教训）：`syncWorstMs` 在 `renderFrame` 之前采样、
       队列水位是瞬时深度非峰值、累计量是本秒差值、`-1`/`-9999` 是哨兵不是零。
       这些说明直接写进报告图例，**不要求读报告的人去翻代码**。
     - 验收：txt 与 json 逐字段一致（脚本自检）；缺任何一项指纹时**拒绝出报告**而非留空；
       每条判据都有实测值 + 交叉校验值两个数字，缺一即标 `INCONCLUSIVE`（不许算 PASS）。

   - **7e 统计口径写死进生成器**（**本次新增的硬要求**）
     - 教训：CPU 这类列单次运行内方差达 30 个百分点，挑几行就能得出相反结论。
       **口径必须由生成器固定，不能交给读报告的人。**
     - 至少写死四条：① **CPU 与所有逐秒列一律整段统计**（给 n / mean / p50 / p95 / max，
       禁止只报某一行）；② **统计窗口显式声明**（起播段、稳态段、每次 seek 后 2 秒
       分别成段，不许混算 —— seek 后的追帧会污染稳态）；③ 每段必须给样本数 n，
       n < 30 的分位数发 `--`；④ **跨轮次对照取 N ≥ 3 次的中位数**，
       确定性段（打开/解析/建链）严格比对，首帧两段单独看分布
       （原「两次差异 < 15%」判定已废，步骤2 实测软解启播 21.3/12.4/11.7ms，
       绝对值太小单次调度抖动即可破 15%）。
     - 验收：同一份 logcat 反复喂给生成器**只能得出同一组数字**；报告里每个统计量
       都标着它的窗口与 n；人为把某一秒删掉后，生成器报"时间线不完整"而不是照算。

   - **7f 基线报告集（真机）**
     - 只用四个性能基线素材：`base-h264-1080p` / `base-hevc-1080p` / `high-4k` / `high-fps`。
       **`tiny-360p` / `no-audio` / `audio-only` / `short-audio` 是行为素材，
       生成器必须拒绝为它们输出性能对照结论**（可出报告，但性能段标「不可作基线」）。
     - 每个素材 × 软解/硬解 各跑 N ≥ 3 次，取中位数，报告落 `test-reports/`。
     - 顺带解掉的既有欠账（见「与步骤3 的合并」）：seek 环形缓冲只保留最近 10 条、
       seek 精度与 ffprobe 关键帧对照、**步骤2 遗留的「seek 后队列峰值归零」**。

## 关键约束（实施时最容易违反，必须遵守）

1. **测量不能影响被测对象**：每帧打点只做 `steady_clock` 取值与直方图累加，
   **不做字符串格式化、不跨 JNI 传原始样本**（60fps 一分钟就是 3600 条）。
   CPU 采样只在面板打开或跑分期间进行。
2. **首帧必须拆成两段**：T5→T6（解码出首帧）与 T6→T7（等同步时钟）分开展示。
   两段优化方向相反——前者要加快解码，后者说明画面已就绪只是在等时钟、
   该动起播锚点策略。合成一个数字会把人引向错误方向
   （先前"起播 0.6s 追平"议题就踩过这个坑）。
3. **硬解与软解的首帧耗时不可直接互比**：T7 的物理含义不同
   （软解 = 提交 GLES/Vulkan 并 swap，硬解 = 交给 SurfaceFlinger），报告里必须有脚注。
   **推广（步骤2 口径纠偏后新增）：口径不同的量绝不能共用字段名。** 同名字段是最隐蔽的
   不可比形态——脚注还有人看，字段名一样则看的人根本不会察觉。凡两条路径含义不同的量，
   一律拆成两个字段、各自只表达一件事，另一条路径留 n=0 → -1 → 上层显示 `--`。
   已按此处理：`videoDecodeMs`（软解，单帧解码 CPU 成本）与 `codecLatencyMs`
   （硬解，codec 端到端延迟，含背压等待）。
4. **禁止 wall clock**：会被系统时间调整/NTP 校准打乱产出负耗时。
   跨语言段以 native 记录为准，不要两个时钟源相减。
5. **样本不足时显示 `--`**：分位数样本 < 30 条时不得给出数字。
6. **跑分报告必须带环境指纹**（机型 / Android 版本 / 素材参数 / 三个策略开关 /
   渲染后端 / 音频后端），缺指纹的报告不能用于对照；中断产出的报告标记「不完整」。
7. **同步余量是丢帧前兆指标**：验收时要确认"余量先下降、丢帧后出现"的顺序，
   顺序颠倒则该指标失去意义。
8. **不新增回调通道**：数值快照走既有拉模式（`getStatsJson` 扩展 +
   `getStartupTraceJson` / `getSeekTraceJson` 两个独立 getter），
   不塞进 `Native → NativeLib.EventHandler → IVEPlayerListener` 事件流。
9. **步骤顺序必须让用户看得见进展（2026-08-08 新增）**：不要把所有可见产出排在末尾。
   有 UI 的 feature，UI 一旦有一路真实数据可展示就先做，**中间层等第二个消费方出现再抽**。
   本 feature 原顺序（四步 native 后才做面板）已被用户反馈证明不可取。

10. **面板读数一律走三态，禁止用默认值兜底（2026-08-09 新增）**：
    `null` → `--`；负数原样显示 + 标红 + 注明"← 负值：采集点顺序颠倒"；正常值正常显示。
    判定基于 `isNull()`，**不得写 `optDouble(key, -1.0)`** ——
    那会把 native 的 `null` 悄悄变回 −1，**等于在 UI 层重新制造 native 层刚消除的状态混淆**
    （"没采到"与"采集点顺序颠倒"又被合成同一个读数）。
    这条已在 2026-08-09 补做（`msOrNull()`），设计稿 3.C 同步。

11. **新指标的两条准入门槛（2026-08-09 新增，设计稿 §8.1）**：
    ① **必须能改变某个决策** —— 说不出"这个数字变了我会做什么"的指标不要加，
    它只增加热路径开销与被误读的机会；
    ② **必须有独立来源可交叉校验** —— 修正后的解码耗时之所以可信，是因为它与线程 CPU 对得上；
    没有第二来源的数字，出错时无人发现（`videoDecodeMs` 连错两次都是因为缺这一步）。

12. **热路径指标一律走已有的 `VEPerfHistogram`（2026-08-09 新增）**：
    单写者无锁、native 侧出分位数。**不得各自造轮子**，否则关键约束 1
    「测量不影响被测对象」这条根本约束就守不住。

13. **报告不能只有聚合值（2026-08-09 新增，设计稿 §8.6）**：现有指标全是聚合快照
    （分位数/峰值/计数），**没有时间线**。卡顿、抖动、水位塌陷只能从时间序列看出来——
    p95 正常但某一秒全塌了，聚合值看不见。步骤7 报告必须输出**逐秒时间线**
    （每秒一行：帧率、丢帧四类、CPU、队列水位、A/V 偏移）。

   > 不能按其原设计去核对。
2. **测量开销反向污染结论**：见关键约束 1；若打点后 CPU 指标本身抬升，
   所有对照数据失效。步骤2 验收必须包含"打点前后无可测退化"。

   进而"各段之和 = 总耗时"校验失败。

5. **seek 精度依赖素材关键帧分布**：验收需固定素材并事先用 ffprobe 取关键帧位置作基准。
6. **跑分序列 60s 期间的外部干扰**：系统后台任务、温控降频会造成跑次间抖动；
   **不要用「两次差异 < 15%」作判定**（步骤2 已证伪，软解绝对值仅约 12ms）：
   N ≥ 3 次取中位数，确定性段严格比对，首帧两段看分布。
7. **面板数据量大拖卡主线程**：六页 + 曲线，需固定长度环形缓冲 + 只刷可见页。
8. **native bug 归属**：本 feature 只负责暴露与可视化，测量中暴露的播放核心缺陷
   归到对应 feature（high-perf-player / vulkan-renderer 等）修，不在本 feature 混改。
