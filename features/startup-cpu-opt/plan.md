# startup-cpu-opt 实施计划（启播与 CPU 优化）

> 设计文档: ../../docs/startup-cpu-opt-design.md
> 创建日期: 2026-08-08

## 方案摘要

用 1080p 真实素材（`/sdcard/Movies/VID_20230814_205835.mp4`，1920×1080 h264 30fps 20Mbps 9.5s + AAC）
重测后，perf-metrics 在 640×360 合成片上得出的瓶颈排序被完全推翻：
**「解析流信息」从 2~4ms 变成 133~145ms，成为启播第一大项**（占总耗时 54%~63%）；
软硬解启播总耗时从"差 8.6 倍"变成基本持平（246.4 / 231.2ms）；
播放中 CPU 两条路都超过一个核（软解 146%、硬解 110.5%）。
按用户批准的顺序做四步：探测参数调优 → 修正软解解码打点 → 日志收敛并复测 CPU → 零拷贝上屏 + codec 预热。

**优化前基线以设计文档 §1 为唯一对照基准**，perf-metrics 的 640×360 数据一律不可用作基线。

## 实施步骤

1. **步骤1 `avformat_find_stream_info` 探测参数调优**
   - 现状：`VEDemux.cpp:412` 以 `nullptr` 选项调用，完全用 FFmpeg 默认上限
     （probesize 5MB / max_analyze_duration 5s / fps_probe_size 20 帧）。
   - 改动：在 `VEDemux.h` protected 段新增虚方法
     `virtual bool probeLimits(int64_t *probeSize, int64_t *maxAnalyzeUs, int *fpsProbeFrames) const`，
     与已有的 `maxTotalBytes()` / `bufferedDurationTargetUs()`（`VEDemux.h:122-123`）同一批钩子并列；
     本地实现给收紧值，`VENetworkSource` 覆写返回 false（**保持 FFmpeg 默认**）。
   - **关键约束：必须区分本地与网络源。** `VENetworkSource`（`VENetworkSource.cpp:85`）覆写
     `openInput` 把字节经自定义 `AVIOContext` 注入，探测期 FFmpeg 会来回 seek；
     网络源用本地的激进值会因**探测数据不足导致轨道漏检** —— 比慢严重得多。
     网络源的瓶颈本来也不在探测，收紧无收益。
   - 具体数值由实测扫描确定，不凭默认值猜。
   - **验收**：1080p 主素材「解析流信息」显著下降；且在**五类素材**上轨道数/编码/**fps**/时长全部正确：
     h264+aac（1080p 主素材）、纯音频 mp3、纯音频 m4a、无音轨 mp4、hevc（设备上 `output_h265.mp4`）。
     **fps 单列一条验收，不与"轨道信息正确"合并** —— `fps_probe_size` 调小后若拿不到 fps，
     `VEAVsync` 会失去帧率信息，症状不是崩溃而是同步判据失效，极易漏过。
     另需核对网络源代码路径确实走的是默认值。

2. **步骤2 修正软解解码耗时打点（perf-metrics 步骤2 的缺陷，本 feature 一并修）**
   - 缺陷：`avcodec_send_packet`（`VEVideoDecoder.cpp:472` / `475`）才是真正干活的地方，
     而计时区间只覆盖 `avcodec_receive_frame` 与格式转换那一侧，**只量到取帧那一侧**。
     证据：1080p 软解报 `videoDecodeMs` p50 = **0.1ms**，
     而同一份数据里 `vdec_thread` 占 **81% CPU**（30fps 摊算每帧约 27ms）—— **差 270 倍**。
   - 方案（累加器）：每次 `send_packet` 的耗时累进成员变量（如 `mPendingSendUs`）；
     **产出一帧时**把「累加值 + 本次 receive/转换耗时」记进直方图并清零，
     得到 **「每产出一帧的解码成本」**。字段注释须与此名称一致。
     一次 send 出多帧时第一帧承担全部 send 成本、后续帧只算 receive（摊销口径，注释写明）。
     flush / seek / EOS 路径必须一并清零，否则残留污染下一帧样本。
   - **必须做的交叉校验**：修正后 p50 × fps 应与 `vdec_thread` CPU 同量级
     （预期 p50 落在 20~30ms、乘 30fps 接近 81%）。0.1ms 能长期挂着没被发现，
     正是因为从未做过这个交叉校验。
   - **这是与硬解那次同源的错误 —— 指标名与实际度量的东西不是同一件事，已连续犯两次**：
     | 次 | 字段 | 名字说的 | 实际量到的 |
     |---|---|---|---|
     | 1 | `videoDecodeMs`（硬解填） | 解码耗时 | pts→出队端到端延迟，绝大部分是背压等待 |
     | 2 | `videoDecodeMs`（软解填） | 解码耗时 | 只有取帧那一侧，不含 send_packet |
     第一次的处置（拆成 `videoDecodeMs` / `codecLatencyMs` + 关键约束"口径不同的量绝不能共用字段名"）
     **没能防住第二次**，因为那条约束管的是"字段名冲突"，而这次是"单个字段自己名不符实"。
     **因此定为新规则：第三次打点前，必须先自问「这个数字的名字，和它量到的东西，是不是同一件事？」**
     落实办法 —— 每个新指标提交前必须给出至少一个独立来源的交叉校验，
     只有单一来源的数字不得进面板。
   - **验收**：交叉校验同量级；flush/seek 后无异常大样本；
     面板/报告标注「口径已修正（2026-08-08 起），与此前 `videoDecodeMs` 数据不可比」。

3. **步骤3 ALOGV 日志收敛并复测 CPU** —— **已完成，结论是假设被证伪**
   > **2026-08-08 实测**：对照实验差值仅 软解 **−1.5pp** / 硬解 **−4.5pp**，
   > **日志不是 CPU 瓶颈**。下文"若差值显著 → 分级收敛"的分支**不触发**，
   > 分级收敛**不做**，降级为可选清理（唯一理由是 logcat 300 行配额）。
   > 落地开关名为 `VE_QUIET_LOG`（默认 OFF），保留作对照实验工具。
   - 怀疑依据：两条路播放中 CPU 都超一个核（软解 146%、硬解 110.5%），
     而**硬解 110.5% 里 `vdec_thread` 只占 23%，其余约 87% 散在几十个小线程上** ——
     "没有热点、到处都热"是每线程共有开销的典型特征。
     密度：`VEPlayer.cpp` 60 处、`VEDemux.cpp` 40 处（**每条消息 3~4 行**）、
     `VEVideoDecoder.cpp` 24、`VEVideoDisplay.cpp` 19、`VEAudioDecoder.cpp` 17；
     1080p 20Mbps 包率下每秒数千次 `__android_log_print`（格式化 + 写 socket 到 logd）。
   - **现有机制已有一半**：`utils/Log.h` 的 `VE_LOG_VERBOSE_ENABLED` 只在 `NDEBUG`
     且未定义 `VE_FORCE_VERBOSE_LOG` 时关闭 V/D/I。
     **但真机测试全部用 `assembleDebug`，即 ALOGV 全开。** 缺的是"Debug 也能关"的开关。
   - 第一件事是**对照实验，不是改代码**：加 `VE_FORCE_QUIET_LOG`（与现有 `VE_FORCE_VERBOSE_LOG` 对称），
     编一版关掉 ALOGV 的，**同素材同配置同设备**软硬解各测 CPU，**差值即答案**。
     本步骤的核心产出是**一个数字**（日志占多少 CPU）。
   - 若差值显著（如 ≥ 20 个百分点）→ 分级收敛（逐帧/逐消息路径 ALOGV 降级或加开关，
     保留状态迁移与异常路径日志）；若不显著 → **结论同样有价值**，
     说明底噪另有来源，转向线程数/消息机制/内存拷贝，别继续猜日志。
   - **必须先证实再动手**，否则改完无法归因（与设计 §0 教训同源）。
   - 附带收益：OPPO PHK110 有单进程 logcat **300 行配额**，日志洪水会把应用自己的
     `Log.i/Log.d` 挤掉（perf-metrics 步骤1 曾因此误判 dumpStartupTrace 没执行，排查很久）。
   - **验收**：产出开/关 ALOGV 的 CPU 对照数字（各 N ≥ 3 次取中位数，记录温控状态）；
     若收敛，状态迁移与异常路径日志仍完整可排查。

4. **步骤4 codec configure 拆分与预热 + 软解首帧不等时钟 + 音频路径 CPU 复查**
   > **2026-08-08 第二次重排。** 第一次定序（4a 零拷贝上屏 → 4b codec 预热 → 4c 音频复查）
   > 已被实测推翻：**零拷贝撤回不做**，其附带项"纹理预分配"**已实施但收益记 0**。
   > **现行定序：4a 硬解 codec configure 拆分与预热 → 4b 软解首帧不等时钟（新增）→ 4c 音频路径 CPU 复查（位置未变）**。
   > 历史结论见下方「4-旧：已撤回/降级的两个子项」与设计文档 §7.6 / §7.7。

   - **4a（当前最大项）硬解 codec configure 拆分与预热**：configure **61~66ms**，
     占硬解启播 **169ms** 的 **39%**，是剩余最大单项。
     - **先拆分再动手**（本步骤第一个交付物）：在 `VEStartupTrace` 增两个里程碑
       `T4A_CODEC_CREATED` / `T4A_CODEC_CONFIGURED`，把 T4a 区间拆成
       **创建 / 配置 / 启动** 三段输出。**拆分数据未出前不写任何优化代码。**
     - 这 66ms 至少含三段：`AMediaCodec_createDecoderByType`（组件加载 + binder 到 codec2 服务）、
       `AMediaCodec_configure`、`AMediaCodec_start`。**哪段占大头决定预热要预热什么**：
       - 若 **createDecoderByType 占大头** → 可在播放器构造时就在后台线程预建一个常用 mime 的
         codec 实例，configure 时复用；
       - 若 **configure 占大头** → 预热无效，方向改为**与 `find_stream_info` 并行**：
         mp4 在 `avformat_open_input` 之后 streams 就已带 `codec_id`/`width`/`height`/`extradata`(avcC)，
         理论上可在 `find_stream_info` 跑的同时并行做 configure，**让两个 66ms 变成一个**。
         这条改动大，需要 demux 在 `open_input` 后就暴露轨道参数。
     - > **拆分已出数（2026-08-08，工作区实测）**：configure 总 **64~87ms** 中
       > `createDecoderByType` 独占 **50~66ms（76~78%）**、`AMediaCodec_configure` 仅 **5.6~7.7ms**。
       > → 走**预热**分支；**"与 `find_stream_info` 并行 configure"那条大改动被否**（只值 5.6~7.7ms）。
       > 落地形态与待验证项见 status.md「4a 工作区现状」与设计文档 §7.8。
     - **反模式（仍然有效）**：把 configure 挪进 prepare 里等它完成**不算优化** ——
       只是把 66ms 从"首帧耗时"搬到"prepare 耗时"，总时长与用户感知完全不变。
       真正收益只能来自**预热**（用等待用户操作的空闲时间提前做完）、**复用**（换源省整次 configure）
       或**并行**（与 `find_stream_info` 重叠）。
     - **验收**：① 三段拆分耗时输出且与现有 T4a 区间自洽；② 优化后以**启播总耗时**判定，
       不接受只有单段变短。

   - **4b（新增）软解首帧不等同步时钟，立即上屏**：来源是 4a-旧 附带项的实测发现 ——
     软解「首帧上屏 57ms」的主体是 **AVSync 等音频时钟起锚**，不是渲染（见下方 4-旧 第 2 条）。
     - 做法：播放器常规套路 —— **先把第一帧画出来，再启动时钟对齐**，首帧不参与同步判据。
       直接压缩感知延迟，**改动比零拷贝小得多**。
     - 风险：首帧可能比音频略早显示，需确认**无可见跳动**（首帧到第二帧不得停顿或回跳）。
     - **验收**：软解 T6→T7 显著下降**且启播总耗时同步下降**；肉眼确认无跳动。

   - **4c（保留原位）音频路径 CPU 复查**：音频路径在软/硬解两条路上都占
     **21~26%** 单核 CPU（`audio_render` 6~8% + `adec` 5.5~6.5% + 系统 `AudioTrack` 9.5~11.5%），
     对 AAC 立体声 44.1k 偏高，且 **1.0x 速率下不该有 sonic 变速开销**。排在 4a/4b 之后。

   - **4-旧：已撤回/降级的两个子项（2026-08-08 实测，保留追溯）**
     1. **~~4a-旧 软解零拷贝上屏~~ → 撤回，不做。**
        拆分 `present` p50 4.4ms 得三段：纹理上传 p50 **1.8** / p95 4.1、绘制 p50 0.3、
        `eglSwapBuffers` p50 **1.8** / p95 3.0。零拷贝只能省"上传"那 1.8ms，
        30fps 下是单核 **5.4%**，在软解总 CPU **144.5%** 里占 **3.7%**。
        代价：`AHardwareBuffer_lockPlanes` 要 **API 29**（minSdk 24）、
        YUV→RGB 交给驱动会**丢掉已修好的 BT.601/709 × full/limited 控制**、
        需要 FFmpeg 自定义 `get_buffer2` + 缓冲池 + EGLImage 生命周期，且仍需保留回退路径。
        **投入产出不成立。**
        **顺带更正归因**：`video_render` 27% CPU 里只有约 **13%** 在 `renderFrame` 内
        （4.4ms × 30fps），另一半在 **AVSync 调度、消息循环、帧队列**上。
        把 27% 整个归给"三平面上传"是不准的。
     2. **纹理预分配 → 已实施并提交，但收益记 0。**
        GLES 纹理改为 prepare 阶段按容器声明尺寸预分配，但**没有改善目标读数**：
        首帧上屏三次实测 **51.7 / 98.2 / 58.8ms**，与预分配前同量级且方差很大。
        原因是**又一次搞错了段落含义** —— T6→T7 量的是「首帧解出 → 提交上屏」，
        **中间包含 AVSync 的等待**，软解带音频时视频首帧在等音频时钟起锚（首声 38.1ms 同量级）。
        **铁证**：同一份数据里 `present` 的 **max 只有 9.98ms**，`renderFrame()` 从来没花过 57ms。
        预分配本身无害（确实省掉首帧的 `glTexStorage2D`×3），**代码保留，收益记 0**。
        真正该做的事变成 **4b**。

## 关键约束

1. **性能基线必须用有代表性的素材**。合成小素材只能验证采集点完整性与字段自洽，
   **不能作为性能基线** —— 它会**系统性单向掩盖**与数据量成正比的瓶颈
   （容器探测/解码/纹理上传/内存）。换素材必须重测**全部**结论，不能只重测怀疑项：
   本次变的不是一个数字，是排序。
2. **每次测量都记录素材指纹**（分辨率/编码/帧率/码率/时长/有无音轨）。
   任何跨素材的数字比较必须显式标注不可比。
3. **打点前先自问「这个数字的名字和它量到的东西是不是同一件事」**，
   并给出至少一个独立来源的交叉校验（见步骤2）。
4. **优化的判定单位是用户感知的总量**（启播总耗时、进程 CPU），不是单段。
   搬移工作量不是优化。
5. **网络源与本地源的探测策略必须分开**（步骤1），网络源保持 FFmpeg 默认。
6. **先对照实验再改代码**（步骤3），否则改完无法归因。
7. ~~本 feature 不新增测量设施~~ → **2026-08-08 放宽**：步骤4a 需在 `VEStartupTrace`
   新增 `T4A_CODEC_CREATED` / `T4A_CODEC_CONFIGURED` 两个里程碑。**拆分测量是动手的前置条件**，
   不算范围蔓延。其余测量仍复用 perf-metrics 的
   `getStartupTraceJson()` / `getStatsJson()` / 性能面板资源页。
8. **（2026-08-08 新增，来自本 feature 第三次同类错误）动手优化某个读数之前，
   先确认它的构成，不能只看它的名字。** 一个里程碑区间/分位数往往由多段组成，
   其中可优化的那段可能只占一小部分，甚至根本不在这个区间里。
   本 feature 已在此栽三次（硬解解码耗时 / 软解解码耗时 / 首帧上屏），
   **三次都是靠先做拆分测量才拦住**：
   | 次 | 读数 | 当时以为 | 拆分后真相 |
   |---|---|---|---|
   | 1 | 硬解 `videoDecodeMs` | 解码耗时 | pts→出队端到端延迟，绝大部分是背压等待 |
   | 2 | 软解 `videoDecodeMs` | 解码耗时 | 只覆盖 receive 侧，不含 `avcodec_send_packet` |
   | 3 | 软解「首帧上屏 57.2ms」 | 首次纹理分配 | 含 AVSync 等音频时钟起锚；`present` max 仅 9.98ms |
   规则升级链条：第 1 次立"口径不同的量不共用字段名"→ 没防住第 2 次；
   第 2 次立"新指标必须有独立来源的交叉校验"→ 没防住第 3 次（采集点与数字都没错，
   错在**读法**：把复合区间当成单一操作的耗时）；**第 3 次追加本条**。

## 依赖与顺序

- 四步按用户批准的顺序执行；**步骤1~3 相互独立可调序**，但步骤4 的内部优先级须等前三步数据。
- **依赖 perf-metrics**：测量手段全部来自它的步骤1/2/5；步骤2 修的是它的缺陷
  （修完须回写 perf-metrics 的 status 备注，两处口径说明保持一致）。
- **与 vulkan-renderer 的冲突面已缩小**（2026-08-08）：零拷贝撤回后，4a 只碰
  `VEStartupTrace` 与 MediaCodec 解码器，**不再与它竞争**；
  但 **4b 首帧路径仍会碰 `VEVideoDisplay` / `VEAVsync`**，动手前仍需确认其工作区状态
  （其步骤7 真机验证仍被"测试机锁屏无法解锁"阻塞、改动仍在工作区）。
- **与 demux-buffering 无改动关系**：原先对它「缓冲按包数封顶」的怀疑已撤回（见下）。
- **与 high-perf-player 的关系**：本 feature 是它性能类验收指标的第一次真实兑现。

## 顺带撤回/降级的两条既有结论

1. **「缓冲按包数封顶」不成立 —— 撤回**。1080p 20Mbps 下视频包峰值只有 **64~71**，
   而 640×360 是 **216**。若按包数设限，高码率素材应同样撞 216；峰值反而更低，
   说明上限本来就按**字节/时长**算（`kMaxTotalBytes` 16MB 全局封顶 + 每路时长达标），
   高码率下自然更早触及字节封顶。**是设计意图，不是缺陷**，不进入本 feature。
2. **「RSS 254MB」降级为待测 —— 不是问题**。该数字在 **640×360** 上测的，
   且**含大量共享库映射**（FFmpeg so、GLES 驱动），RSS 口径本身把共享页算进来。
   1080p 下**未单独测过内存**。要判断需专门测一轮：区分 RSS/PSS/native heap 三个口径，
   同素材做"播放前 vs 播放中"差分。是否立项等那轮数据。

## 风险

1. **步骤1 收紧探测导致轨道/fps 漏检**（最高风险，症状隐蔽）——
   五类素材逐项核对，fps 单列验收；网络源不参与收紧。
2. 步骤1 收益随素材而异 —— 每素材记录实测值，不用单一素材下结论。
3. 步骤2 修正后数字从 0.1 变成约 27ms，**会被误读为性能退化** ——
   必须标注"口径已修正、与此前数据不可比"及修正日期。
4. 步骤3 对照实验受温控降频干扰 —— 同轮内交替测量、N ≥ 3 取中位数、记录设备温度状态。
5. ~~步骤4a 与 vulkan-renderer 碰同一批文件~~ → 零拷贝撤回后已消解；
   **改为：步骤4b（首帧路径）仍碰 `VEVideoDisplay`/`VEAVsync`，动手前确认对方工作区状态。**
6. 步骤4a 做成"把 configure 挪进 prepare"的假优化 —— 验收看启播总耗时。
7. 本 feature 的改动会让 perf-metrics 的 640×360 旧基线全部失效 ——
   以设计 §1 的 1080p 数据为唯一对照基准。
8. **（新增）4a 拆分数据出来前就开始写优化代码** —— 三次同类错误（关键约束 8）都是这么来的。
   拆分里程碑出数是 4a 的第一个交付物。
9. **（新增）4a「configure 与 `find_stream_info` 并行」改动面大** —— 需 demux 在 `open_input`
   后暴露早期轨道参数；只在拆分数据显示"配置占大头"时才走，并评估网络源/非 mp4 容器
   （extradata 可能缺失）的兼容性。
10. **（新增）4b 首帧不等时钟导致可见跳动** —— 首帧到第二帧不得停顿或回跳，
    必要时限定"仅首帧豁免"。
