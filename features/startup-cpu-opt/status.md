## 触发背景：1080p 真实素材推翻了小素材上的结论

perf-metrics 全部测量此前用的是 ffmpeg 造的 **640×360** 合成片。换 1080p 真实素材后瓶颈排序完全变了：

| | 640×360 合成片 | 1920×1080 真实素材 | 变化 |
|---|---|---|---|
| 解析流信息 | 2.4 / 2.1ms | **145.0 / 133.8ms** | 约 60 倍，从可忽略项跃升为**启播第一大项** |
| 启播总耗时（硬解） | 101.7ms | 231.2ms | 2.3 倍 |
| 启播总耗时（软解） | 11.8ms | 246.4ms | 20.9 倍；软硬解从"差 8.6 倍"变成**基本持平** |

旧结论"硬解起播比软解慢 8.6 倍、瓶颈是 MediaCodec configure"是那份数据的正确读法，
但它是**素材的性质**而不是播放器的性质。**解析流信息这个瓶颈在小素材上完全不可见。**

方法论教训（已写进设计文档 §0 与 plan 关键约束 1/2）：
性能结论必须用有代表性的素材得出；合成小素材会**系统性单向掩盖**真实瓶颈；
换素材必须重测全部结论 —— 本次变的不是一个数字，是排序。

## 已撤回/降级的三条结论（2026-08-08）

1. **「缓冲按包数封顶」不成立 —— 从优化建议中撤回**。1080p 20Mbps 视频包峰值仅 **64~71**，
   640×360 是 **216**；若按包数设限高码率应同样撞 216。说明上限本来就按字节/时长算
   （16MB 全局字节封顶 + 每路时长达标），高码率下更早触及字节封顶。是设计意图，不是缺陷。
   已同步标注进 perf-metrics 的 status。
2. **「RSS 254MB」降级为待测 —— 不是问题**。该值测于 640×360 且含大量共享库映射；
   1080p 下未单独测内存。要判断需专门测一轮（RSS/PSS/native heap 三口径 +
   播放前后差分），是否立项等数据。已同步标注进 perf-metrics 的 status。
3. **「ALOGV 洪水是 CPU 底噪主因」—— 步骤3 对照实验证伪，撤回**（软解 −1.5pp、硬解 −4.5pp）。
   日志收敛降级为可选清理，理由只剩 logcat 300 行配额。
   perf-metrics status 里那条「建议起日志分级收敛任务」的性能理由已同步标注为已证伪。
