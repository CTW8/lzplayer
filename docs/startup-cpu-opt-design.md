# 启播与 CPU 优化设计文档（startup-cpu-opt）

> 创建日期: 2026-08-08
> 状态: Doing
> 数据来源: OPPO PHK110 / Android 16 / ColorOS 真机实测（perf-metrics 步骤1/2/5 建成的采集能力）

---

## 0. 前置教训：性能结论必须用有代表性的素材得出

**本 feature 的存在本身就是一次方法论纠错。**

perf-metrics 的全部测量（步骤1 的启播里程碑基线、步骤2 的稳态分位数基线）用的都是
用 ffmpeg 造的 **640×360 合成片**。换成设备上的真实素材
`/sdcard/Movies/VID_20230814_205835.mp4`（1920×1080 h264 30fps 20Mbps 9.5s 带 AAC）
重测后，**瓶颈排序完全变了**：

| | 640×360 合成片 | 1920×1080 真实素材 | 变化 |
|---|---|---|---|
| 解析流信息 | 2.4 / 2.1ms | **145.0 / 133.8ms** | **约 60 倍，从可忽略项跃升为第一大项** |
| 启播总耗时（硬解） | 101.7ms | 231.2ms | 2.3 倍 |
| 启播总耗时（软解） | 11.8ms | 246.4ms | **20.9 倍，且软硬解从「差 8.6 倍」变成「基本持平」** |

在小素材上，"硬解起播比软解慢 8.6 倍，瓶颈是 MediaCodec configure" 这个结论看着无懈可击——
它确实是那份数据的正确读法。但它是**素材的性质**，不是播放器的性质：
软解 640×360 一帧只要 2.4ms，1080p 就要 49.6ms；`avformat_find_stream_info`
要读够足够的数据来定编码参数与帧率，20Mbps 码流下它读的字节数是 640×360 的几十倍。

**沉淀为规则（写进本 feature 的关键约束，也适用于后续所有性能工作）：**

1. **性能基线必须用有代表性的素材建立。** 合成小素材只能用于验证采集点是否完整、
   字段是否自洽，**不能作为性能基线**，因为它会**系统性掩盖**（不是随机噪声，是单向掩盖）
   与数据量成正比的那些瓶颈：容器探测、解码、纹理上传、内存。
2. **换素材必须重测全部结论**，不能只重测怀疑的那一项——上表里变的不是一个数字，是排序。
3. 报告里必须带素材指纹（分辨率/编码/帧率/码率/时长/有无音轨）。
   perf-metrics 步骤7 的环境指纹要求本来就包含这条，本次教训是它**必须前置到每一次手工测量**，
   而不是只在跑分报告里出现。

## 1. 背景与目标

### 优化前基线（本 feature 的唯一对照基准）

**环境**：OPPO PHK110 / Android 16 / ColorOS，arm64-v8a，8 核，Debug 构建（ALOGV 全开）。
**素材**：`/sdcard/Movies/VID_20230814_205835.mp4` —— 1920×1080 h264 30fps 20Mbps 9.5s + AAC。

#### 1.1 启播分段（ms）

| 段 | 硬解 | 软解 | 说明 |
|---|---|---|---|
| 打开容器 | 5.2 | 5.0 | `avformat_open_input` |
| **解析流信息** | **145.0** | **133.8** | `avformat_find_stream_info` —— **第一大项** |
| 建链 | 0.7 | 0.7 | 仅接线耗时（configure 异步，不在此段内） |
| 解码器 configure | 66.3 | 0.5 | **叠加区间**，落在首帧窗口内，不计入分段和 |
| 首帧解码 | 79.6 | 49.6 | T5→T6 |
| 首帧上屏 | 0.7 | 57.2 | T6→T7；软解此项是**首次纹理分配** |
| **启播总耗时** | **231.2** | **246.4** | (T4−T0) + (T7−T5) |

结构性结论：
- **解析流信息占总耗时的 54%（软解）/ 63%（硬解，扣掉叠加项后）**，是唯一软硬解都吃的大项。
- 硬解第二大项是 configure 66.3ms；软解第二、三大项是首帧上屏 57.2ms 与首帧解码 49.6ms。
- **软硬解总耗时在 1080p 上基本持平**（246.4 vs 231.2），
  与 640×360 上「硬解慢 8.6 倍」的旧结论相反。

#### 1.2 稳态（播放中）

| 指标 | 硬解 | 软解 |
|---|---|---|
| 进程 CPU（单核归一） | 110.5% | 146% |
| 进程 CPU（整机，8 核） | 13.81% | 18.25% |
| 上屏 p50 / p95 | 1.5 / 2.7ms | 5.3 / 8.5ms |
| 同步余量 p50 / p95 | 12.0 / 32.5ms | 5.0 / 29.0ms |
| 丢帧 | 0 / 278 | 0 / 287 |

线程 CPU 分布：

| 路径 | 线程 | CPU |
|---|---|---|
| 软解 | `vdec_thread` | 81% |
| 软解 | `video_render` | 27.5% |
| 硬解 | `vdec_thread` | 23% |
| 硬解 | NDK MediaCodec 相关 | 10.5% |
| 硬解 | HwBinder | 7% |

结构性结论：
- **两条路都超过一个核**（110.5% / 146%），而 30fps 1080p 在这个档位的 SoC 上不该这么贵。
- **硬解 110.5% 里 `vdec_thread` 只占 23%，其余约 87% 散在几十个小线程上** ——
  这种"没有热点、到处都热"的分布是**每线程共有开销**的典型特征，最可疑的是日志。
  > **2026-08-08 证伪**：步骤3 对照实验表明日志只值 1.5~4.5pp。
  > 散开的 CPU 实际主要在**音频路径（21~26%）** 与 MediaCodec/HwBinder 上，见 §7.4。
- 丢帧 0、同步余量 p95 仍有 29~32.5ms 余量 → **当前不掉帧，但 CPU 余量已经很薄**，
  换更高帧率素材或更弱设备就会破。

### 目标

按用户批准的顺序，四步各自独立可验证：

1. 削掉启播第一大项：`avformat_find_stream_info` 的 133~145ms。
2. 修正软解解码耗时打点——**当前这个数字是错的**（报 0.1ms，实际约 27ms），
   先让数字可信，再谈优化。
3. 查清并收敛播放中的 CPU 底噪（怀疑 ALOGV 洪水）。
4. 软解上屏零拷贝 + 硬解 codec 预热（优先级待前三步数据后再定）。

### 非目标

- 不做 Vulkan 渲染（归 vulkan-renderer）。
- 不改 demux 缓冲策略（归 demux-buffering，且**下方 §4.1 已撤回原先对它的怀疑**）。
- 不做内存优化（RSS 尚未在 1080p 上测过，见 §4.2，需先测再定是否立项）。

## 2. 技术方案

### 步骤1：`avformat_find_stream_info` 探测参数调优

#### 现状

`VEDemux::onPrepare`（`VEDemux.cpp:412`）以 `nullptr` 选项调用
`avformat_find_stream_info`，即完全用 FFmpeg 默认探测上限：
`probesize` 默认 5MB、`max_analyze_duration` 对多数容器为 5s、
`fps_probe_size` 默认 20 帧。20Mbps 码流下这意味着要读数 MB 并解若干帧才返回。

#### 方案

在 `find_stream_info` 前设置探测上限，来源为一个新增的 **虚方法**，本地源给激进值、
网络源保持 FFmpeg 默认：

```
// VEDemux.h protected 段，与已有的 maxTotalBytes() / bufferedDurationTargetUs()
// 同一批虚钩子并列
/// 探测上限。返回 false 表示"用 FFmpeg 默认"（网络源即如此）。
virtual bool probeLimits(int64_t *probeSize, int64_t *maxAnalyzeUs, int *fpsProbeFrames) const;
```

- `VEDemux`（本地）：给收紧后的值，具体数值以步骤1 的实测扫描确定。
- `VENetworkSource`：覆写返回 `false`（保持默认）。

#### 为什么必须区分本地与网络源（关键约束）

`VENetworkSource` 继承 `VEDemux` 并覆写 `openInput`（`VENetworkSource.cpp:85`），
把字节经自定义 `AVIOContext` 注入，FFmpeg 只做 demux。这条路上：

- 探测期 FFmpeg 会**来回 seek**（`avioSeek` 已按此做了不重开连接的优化），
  探测数据不足会直接导致**轨道漏检**——比慢得多严重。
- 网络源的"读得少"省不下 CPU，省下的是网络往返，而它的瓶颈本来就不在探测。
- 因此**网络源一律保持 FFmpeg 默认值**，不参与本步骤的收紧。

这也是把它做成虚方法而不是常量的原因：与 `maxTotalBytes()` / `bufferedDurationTargetUs()`
同一模式，让每种源自己声明自己的探测策略。

#### 风险与验收要求

收紧探测上限的代价是**信息可能拿不全**，必须在多种素材上逐项核对
（轨道数 / 编码 / **fps** / 时长）：

| 素材类型 | 必须核对 |
|---|---|
| h264 + aac（1080p 主素材） | 轨道数 2、编码正确、fps=30、时长 9.5s |
| 纯音频 mp3 | 只有音轨、无视频轨误报、时长正确 |
| 纯音频 m4a | 同上 |
| 无音轨 mp4 | 只有视频轨、`decodePath` 与 `totalBasis` 仍正确 |
| hevc（设备上 `output_h265.mp4`） | 编码识别为 hevc、fps、时长 |

**`fps` 是最容易被这次改动打坏的一项**：`fps_probe_size` 调小后若拿不到帧率，
`VEAVsync` 会失去帧率信息（帧间隔推算、同步余量计算都依赖它），
症状不是崩溃而是**播放不流畅/同步判据失效**，很容易漏过。
所以验收里 fps 单列一条，不与"轨道信息正确"合并。

### 步骤2：修正软解解码耗时打点

#### 缺陷（perf-metrics 步骤2 引入，在本 feature 一并修）

`videoDecodeMs` 直方图的打点位置只覆盖了 `avcodec_receive_frame` 与格式转换那一侧，
**`avcodec_send_packet`（`VEVideoDecoder.cpp:472` / `475`）——真正干活的地方——不在计时区间内**。

后果，用同一份 1080p 软解数据自相矛盾即可看出：

| 证据 | 数值 | 含义 |
|---|---|---|
| `videoDecodeMs` p50 | **0.1ms** | 打点报出来的"解码耗时" |
| `vdec_thread` CPU | **81%** | 30fps 摊算 → **每帧约 27ms** |

**差 270 倍。** 这个数字不是偏差，是量错了对象。

#### 方案：累加器

libavcodec 的 send/receive 不是一一对应（一次 send 可能出 0 帧或多帧），
所以不能简单地把 send 的耗时并进某一帧：

1. 每次 `avcodec_send_packet` 的耗时累进一个成员变量（如 `mPendingSendUs`）。
2. **产出一帧时**，把 `mPendingSendUs + 本次 receive/格式转换耗时` 作为一条样本记进直方图，
   随后 `mPendingSendUs` 清零。
3. 得到的量是 **"每产出一帧的解码成本"** —— 这个名字必须与实现一致地写进注释与设计。
4. 一次 send 出多帧时，第一帧承担全部 send 成本、后续帧只算 receive
   （这是"每产出一帧的摊销成本"的定义使然，需在字段注释里写明，不要让读数的人以为是每帧对称的）。
5. flush / seek / EOS 路径上必须一并清零累加器，否则跨 flush 的残留会污染下一帧样本。

**自校验（本步骤必须做的验收）**：修正后的 `videoDecodeMs` p50 × fps
应与 `vdec_thread` 的 CPU 占用同量级（1080p 软解预期 p50 落在 20~30ms、
乘 30fps 后接近 81%）。**两个独立来源互相印证，才算这个数字可信。**
原先的 0.1ms 之所以能长期挂着没人发现，正是因为**没做过这个交叉校验**。

#### 这是同源错误的第二次（必须记住的教训）

| 次 | 字段 | 名字说的 | 实际量到的 |
|---|---|---|---|
| 1 | `videoDecodeMs`（硬解填） | 解码耗时 | pts→出队端到端延迟，**绝大部分是背压等待** |
| 2 | `videoDecodeMs`（软解填） | 解码耗时 | **只有取帧那一侧**，不含 send_packet |

两次的病根**完全相同**：**指标名与它实际度量的东西不是一回事。**
第一次的处置是拆字段（`videoDecodeMs` / `codecLatencyMs`）并写进关键约束
"口径不同的量绝不能共用字段名"——**那条约束没能防住第二次，因为它管的是"字段名冲突"，
而这次是"单个字段自己就名不符实"。**

**因此新增一条更前置的规则：第三次打点前，先自问
「这个数字的名字，和它量到的东西，是不是同一件事？」**
落实办法：每个新指标在提交前必须给出**至少一个独立来源的交叉校验**
（如本次的"分位数 × 帧率 ≈ 线程 CPU"），只有单一来源的数字不得进面板。

### 步骤3：ALOGV 日志收敛并复测 CPU

#### 怀疑对象

`utils/Log.h` 现有机制：`VE_LOG_VERBOSE_ENABLED` 仅在 `NDEBUG` 且未定义
`VE_FORCE_VERBOSE_LOG` 时关闭 V/D/I 三级。**Debug 构建（`assembleDebug`，即全部真机测试所用）
下 ALOGV 全量输出。**

密度：`VEPlayer.cpp` 60 处、`VEDemux.cpp` 40 处、`VEVideoDecoder.cpp` 24 处、
`VEVideoDisplay.cpp` 19 处、`VEAudioDecoder.cpp` 17 处。其中 **`VEDemux` 每条消息打 3~4 行**,
1080p 20Mbps 的包率下就是**每秒数千次 `__android_log_print`**，
每次含格式化 + 写 socket 到 logd。

这与 §1.2 的观察吻合：**硬解 110.5% 里主线程只占 23%，其余散在几十个小线程上** ——
日志开销正是这样"每线程都摊一点"的形态。

#### 干净的对照实验（本步骤的核心，先证实再动手）

新增一个**强制静默**的编译开关（现有机制是"Release 关"，缺的是"Debug 也能关"）：

```
// Log.h：与已有 VE_FORCE_VERBOSE_LOG 对称
#if defined(VE_FORCE_QUIET_LOG)
#define VE_LOG_VERBOSE_ENABLED 0
#elif defined(NDEBUG) && !defined(VE_FORCE_VERBOSE_LOG)
...
```

然后**同素材、同配置、同一台设备**各测一轮 CPU（软硬解各一次），
**差值即答案**。这一步的产出是**一个数字**（日志占了多少 CPU），不是代码改动。

- 若差值显著（例如 ≥ 20 个百分点）→ 做分级收敛：
  逐帧/逐消息路径上的 ALOGV 降级或加编译开关，保留状态迁移与异常路径的日志。
- 若差值不显著 → **结论同样有价值**：说明 CPU 底噪另有来源，
  应转向线程数/消息机制/内存拷贝去查，而不是继续猜日志。

**必须先做对照再改代码**，否则改完无法归因（这正是 §0 教训的同一类问题）。

#### 实测结论（2026-08-08）：假设被证伪，本步骤的优化定位撤回

对照实验做完了，**答案是"日志不是 CPU 瓶颈"**：

| | 日志全开 | 静音日志 | 差值 |
|---|---|---|---|
| 软解 CPU（单核归一） | 146% | 144.5% | **−1.5pp** |
| 硬解 CPU（单核归一） | 110.5% | 106.0% | **−4.5pp** |

上文"硬解 110.5% 里主线程只占 23%、其余散在几十个小线程上 ⇒ 每线程共有开销 ⇒ 日志"
这条推理**是错的**。散开的 CPU 另有来源（见 §7.4 的实测构成：软解主要在 `vdec_thread`
与 `video_render`，硬解主要在音频路径与 HwBinder）。

**处置：日志收敛从性能优化项中撤回，降级为"可选清理"。** 保留它的唯一理由是
下文「附带收益」那条——设备 logcat 300 行配额。开关本身保留作为对照实验工具。

实际落地的开关名与本节示例不同（以代码为准）：`utils/Log.h` 的条件为
`#if defined(VE_QUIET_LOG) || (defined(NDEBUG) && !defined(VE_FORCE_VERBOSE_LOG))`，
`CMakeLists.txt` 加 `option(VE_QUIET_LOG ... OFF)`，`lzplayer_core/build.gradle`
支持 `-PveQuietLog=true` 传下去。**默认 OFF**。

#### 附带收益

OPPO PHK110 有**单进程 logcat 300 行配额**，超出静默丢弃。
日志洪水会把应用自身的 `Log.i/Log.d` 一起挤掉——perf-metrics 步骤1 曾因此
误判 "dumpStartupTrace 没执行"，反复重装排查很久。收敛日志直接改善后续所有 feature 的可调试性。

### 步骤4：零拷贝上屏 + codec 预热

**原文写"优先级待前三步数据后再定"。数据已到（2026-08-08），排序如下（依据见 §7.4）：**

| 序 | 子项 | 依据 |
|---|---|---|
| 1 | **4a 零拷贝上屏**（含首帧纹理预分配） | 软解路径最大可优化项：上屏 p50 5.7 / p95 8.2ms，`video_render` 27.0% CPU = 软解总 CPU 的 **18.7%**；软解首帧上屏 57.2ms 是首次纹理分配，可预分配掉 |
| 2 | **4b codec 预热/复用** | 硬解启播剩余最大项：configure 61~66ms |
| 3 | **4c 音频路径 CPU 复查**（新增子项） | 音频路径在软/硬解两条路上都占 **21~26%** 单核 CPU，对 AAC 立体声 44.1k 偏高，见 §7.5 |

步骤3 并未如预期改变 CPU 分布（只值 1.5~4.5pp），所以排序由步骤1/2 的数据与静音日志后的
线程构成决定，与本节原有的 4a/4b 判断方向一致。

#### 4a. 软解零拷贝上屏

依据：软解上屏 p50 **5.3ms**、`video_render` 线程 **27.5% CPU**，
是 1080p **三平面 YUV 经 GLES 逐平面上传**的代价（数据量 = 1920×1080×1.5，每帧约 3MB）。

方向：`AHardwareBuffer` + `EGLImage` 零拷贝，让解码输出直接作为纹理内存，消掉 `glTexSubImage2D`。
**比 vulkan-renderer 那条路更直接见效**——瓶颈是内存带宽与拷贝，不是图形 API 的提交开销，
换 API 不消拷贝则收益有限。

附带项：软解**起播首帧上屏 57.2ms**（对比稳态 p50 5.3ms，差 10 倍）是**首次纹理分配**，
可在 prepare 阶段按已知分辨率**预分配**掉。这是纯启播收益，与零拷贝独立，可先做。

#### 4b. 硬解 codec 预热

依据：硬解 configure **66.3ms**，扣掉步骤1 的收益后会成为第一或第二大项。

方向：codec 实例预热 / 复用（进入播放界面即按常见参数创建，或跨换源复用同一 codec）。

**明确的反模式（必须写进设计，避免做出假优化）**：
**把 configure 挪进 prepare 里等它完成，不算优化。**
那只是把这 66ms 从"首帧耗时"搬到"prepare 耗时"，
**总时长与用户感知完全不变**，却会让瀑布图上的首帧段变短、看着像优化了。
真正的收益只能来自**预热**（把 configure 提前到用户还没选片时就做完，
用等待用户操作的空闲时间换）或**复用**（换源时省掉整次 configure）。

这条同时是对 perf-metrics 采集口径的保护：启播总耗时定义为 `(T4−T0) + (T7−T5)`，
搬移工作量会同时改变 T4 与 T7，**总数不变**——这个定义本身就是抗这类假优化的，
不要为了让数字变好而改定义。

## 4. 需要撤回/降级的既有结论

以下两条是上一轮基于 640×360 数据得出的错误结论，一并更正：

### 4.1 「缓冲按包数封顶」这个担心不成立 —— 撤回

原怀疑：视频包队列峰值 216 疑似撞上按包数的上限，导致缓冲深度受限。

**实测证伪**：1080p 20Mbps 下视频包峰值只有 **64~71**，而 640×360 是 **216**。
若上限按包数算，高码率素材应该同样撞到 216。峰值反而更低，
说明**上限本来就是按字节/时长算的**（`kMaxTotalBytes` 16MB 全局字节封顶 +
每路时长达标，见 demux-buffering 设计），高码率下自然更早触及字节封顶、包数因此更少。
**行为是设计意图，不是缺陷。** 该项从优化建议中撤回，不进入本 feature。

顺带的正面结论：这也说明 demux-buffering 的"全局字节封顶为唯一硬停"策略在高码率下工作正常。

### 4.2 「RSS 254MB」降级为待测 —— 不是问题

原观察：性能面板资源页显示 RSS 254MB，疑似偏高。

**该数字不可用于判断**，两个原因：
1. 它是在 **640×360** 素材上测的；
2. 它**含大量共享库映射**（FFmpeg 各 so、GLES 驱动等），RSS 口径本身就把共享页算进来。

1080p 下**没有单独测过内存**。因此该项标为 **待测**，不是问题。
要判断需专门测一轮：区分 RSS / PSS / native heap 三个口径，
并在同一素材上做"播放前 vs 播放中"的差分。是否立项等这轮数据。

## 7. 实施结论（步骤1~3，2026-08-08 真机验证）

环境与素材与 §1 基线完全一致：OPPO PHK110 / Android 16 / ColorOS，8 核，Debug 构建；
主素材 `/sdcard/Movies/VID_20230814_205835.mp4` = 1920×1080 h264 30fps 20Mbps 9.5s + AAC。

### 7.1 步骤1：探测调优 —— 达成，解析流信息降 54%~62%

落地形态：`VEDemux.h` 新增 `struct ProbeLimits { probeSizeBytes; analyzeDurationUs; fpsProbeFrames; }`
与 `virtual probeLimits()`，本地默认 **512KB / 1s / fpsProbeFrames=0**；
`VEDemux.cpp` 在 `avformat_find_stream_info` 之前套用（`probesize` / `max_analyze_duration`
是结构体字段，**`fpsprobesize` 只有 AVOption、没有结构体字段，须走 `av_opt_set_int`**），
并打一条 ALOGI 记录实际生效值。
`VENetworkSource.h` 覆写返回 `{0, 0, -1}` = **沿用 FFmpeg 默认**。

| | 解析流信息 | 启播总耗时 |
|---|---|---|
| 硬解 优化前 → 后 | 145.0 → **66.1ms**（−54%） | 231.2 → **169.0ms**（−27%） |
| 软解 优化前 → 后 | 133.8 → **51.1ms**（−62%） | 246.4 → **209.1ms**（−15%） |

其它素材解析耗时：hevc **0.7ms**、无音轨 mp4 **2.4ms**、纯音频 m4a **1.5ms**、mp3 **1.0ms**。

**功能验证（本步骤的关键验收，风险 1 就是冲它来的）全部通过：**
- 时长 9529ms 与 `ffprobe` **完全一致**；
- codec 正确识别为 `h264`；
- 纯音频文件 codec 正确为 `-`、渲染 0 帧、音频后端 AAudio；
- 渲染帧数 硬解 **278** / 软解 **287**，**与调优前完全一致**
  —— 注意这不是回归：278/287 在调优前就是这两个数字；
- **fps 无直接读取途径**，间接验证：287 帧 / 9.529s = **30.1fps**，与 30fps 源一致且丢帧 0，
  说明 `VEAVsync` 仍拿到了帧率。

**为什么网络源必须排除（实施后再次确认）**：网络源字节要现拉，探测量不足会**漏轨道或拿不到 fps**
—— 那是功能缺陷，不是可以用来换启播速度的东西。

遗留：66ms 仍不算小。512KB 在 20Mbps 下只有约 **0.2s** 数据，而 `find_stream_info`
仍需为每条流解出至少一帧来确定像素格式，这部分是**固有成本**。
继续压 probesize 收益递减而漏轨风险上升，**暂不再动**。

### 7.2 步骤2：解码打点修正 —— 达成，交叉校验同量级

`VEVideoDecoder` / `VEAudioDecoder` 各加成员 `mDecodeAccumUs`：`avcodec_send_packet`
前后计时累加；产出一帧时把「累加值 + 本次 receive/转换耗时」记进直方图并清零；
**`onFlush` 里清零**（否则已送包但未结算的耗时会挂到 flush 后第一帧上）。

| 指标（1080p 软解） | 修正前 | 修正后 |
|---|---|---|
| 视频解码 p50 | 0.1ms | **14.0ms**（p95 23.6，max 60.25，n=287） |
| 音频解码 p50 | 0.05ms | **0.3ms**（p95 0.65，n=445） |

**交叉校验（§6 验收 3）**：`vdec_thread` 79.5% CPU ÷ 30fps = 每帧约 **26.5ms** CPU，
与实测 wall p50 14 / p95 23.6 **同量级**。差值来自取包、`VEFrame` 分配等落在测量窗口外的部分，
以及 FFmpeg 内部多线程解码的工作不全计入 `vdec_thread` 自身。

修正后的值比原预期（20~30ms）略低，但仍在同量级，结论成立。
**面板/报告须标注「口径已于 2026-08-08 修正，与此前 `videoDecodeMs` 数据不可比」（风险 3）。**

### 7.3 步骤3：假设被证伪 —— 见 §2 步骤3「实测结论」

一句话：**ALOGV 洪水不是 CPU 瓶颈，只值 1.5~4.5 个百分点**，日志收敛从优化项撤回。
开关默认 OFF 保留作对照工具。对照实验有效性已确认（静音版 `VEDemux` verbose 日志条数为 0）。

### 7.4 静音日志后的 CPU 构成（1080p，步骤4 排序的依据）

| 路径 | 总计 | 构成 |
|---|---|---|
| 软解 | **144.5%** | `vdec_thread` **79.5%**（FFmpeg 1080p30 h264 真解码，固有成本）+ `video_render` **27.0%**（GLES 三平面上传）+ 音频路径约 **21%**（AudioTrack 9.5 / audio_render 6.0 / adec 5.5） |
| 硬解 | **106.0%** | `vdec_thread` 24% + NDK MediaCodec 14.5% + 音频路径约 **26%**（AudioTrack 11.5 / audio_render 8.0 / adec 6.5）+ HwBinder 7% |

硬解比软解省 **38.5pp**，几乎全部省在解码本身（79.5 → 24）。

### 7.5 新观察：音频路径 CPU 偏高（步骤4c 的由来）

**音频路径在软/硬解两条路上都占 21~26% 单核 CPU**，对 **AAC 立体声 44.1k** 而言偏高，
且 1.0x 速率下**不该有 sonic 变速开销**。构成为 `audio_render` 6~8% + `adec` 5.5~6.5% +
系统 `AudioTrack` 9.5~11.5%。**值得单独查一次**，已登记为步骤4 的第三优先子项。
