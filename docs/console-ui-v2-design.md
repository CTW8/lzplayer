## 1. 背景与命题

### 1.1 一句话命题

**从「播放器 + 一堆入口」变成「仪表台 + 播放窗」。**

### 1.2 为什么要改

测试台的判定标准从第一版起就是两句话：

> 每项能力都有**可按到的控件**，每项内部状态都有**当场可读的读数**。

第一半做到了 —— 播放/暂停/seek/速率/循环/轨道/字幕/强制软解/强制 SLES 都有控件。
**第二半没有**：读数几乎全部藏在 BottomSheet 面板里，主屏只有 HUD 上寥寥两三项。
结果是主屏答不了那个最该被秒答的问题 —— **"现在健康吗？"**

同时存在一处空间浪费：竖屏下 1080p 横向素材只占屏幕中间一条，**上下两片黑边**
恰好是这些读数该待的地方。把黑边换成常驻仪表带，不需要牺牲画面。

### 1.3 上一版的具体教训（必须写进设计的部分）

- **教训 A：读数旁边不写素材规格，数字就没有意义。**
  这一轮反复出现的事故是：同一份代码在 640×360 与 1080p 上**瓶颈排序完全不同**
  （解析流信息 2~4ms → 133~145ms，从可忽略项跃升为启播第一大项）。
  所以画面区的 chip 必须把**分辨率与帧率**写上：`SW · h264 · 1080p30`。
  没有素材规格的读数是不可比、不可归档的。

- **教训 B：问题不在按钮数量，在把四种不同性质的控件混排。**
  上一版把「主操作 / 参数选择 / 开关 / 破坏性动作」挤在同一行，
  8 个按钮用了 3 套视觉语言，越试图"分级"越乱。

- **教训 C：仪表与细节页之间没有连接，等于把归因工作丢回给人。**
  八项读数分散在诊断面板的三个分页里，某格变红时用户得自己开面板、自己猜看哪一页。
  这个映射关系用户凭什么知道。

## 2. 三条设计约束（本 feature 的硬约束，实施中不得违反）

### 约束 1：控件按性质分三层，每层只用一种视觉语言

| 层 | 视觉语言 | 承载内容 | 数量上限 |
|----|----------|----------|----------|
| ① 主操作 | **圆钮**（26px，内嵌进度行） | 播放/暂停 —— **唯一**主操作 | 1 |
| ② 面板入口 | **描边框**，四等宽，样式完全一致 | 性能 / 轨道 / 字幕 / 跳转 | 4 |
| ③ 次要控件 | **纯文字，无框** | 速率 ▾ / 循环 / 停止 | 3 |

同一层内**不允许**出现第二种样式（不许某个入口特别宽、特别亮、带副标题）。

### 约束 2：优先级不靠颜色和尺寸强调，靠顺序和位置

上一版给「性能」做 1.7 倍宽 + 主色 + 副标题，给「停止」做专属危险色小块 ——
这都是在**增加样式种类**来表达优先级。本版一律改为：

- 「性能」最常用 → **排在四个入口的第一个**，样式与其余三个完全相同。
- 「停止」是破坏性动作 → **靠右放置 + 危险色字色**，不做色块、不加边框。
- 降级只用**位置和字色**，不用尺寸和背景。

### 约束 3：测试台要密度不要大按钮

全宽填充的播放键是消费级播放器思路。**主屏的价值在读数，不在 chrome。**
播放键缩成 26px 圆钮内嵌进度行，省下的整整一行高度归仪表带；
面板入口高度砍到原来的一半左右。

## 3. 竖屏布局（自上而下）

```
┌──────────────────────────────────────────────┐
│ 1. 源栏（折叠态）  VID_2023…mp4  1080p  [换源]│  ← 一行
├──────────────────────────────────────────────┤
│ 2. 画面区                                     │
│      chip: SW · h264 · 1080p30    状态/速率   │
├──────────────────────────────────────────────┤
│ 3. 常驻仪表带（两行八格）★本次核心            │
│    帧率   丢帧(迟到)   A/V     CPU            │
│    启播   同步余量     队列音视  缓冲          │
├──────────────────────────────────────────────┤
│ 4. 进度行  (▶) ━━━━━●────────  00:12 / 00:09.5│  ← 圆钮内嵌
├──────────────────────────────────────────────┤
│ 5. 面板入口  [性能][轨道][字幕][跳转]         │  ← 四等宽描边，同样式
├──────────────────────────────────────────────┤
│ 6. 次要控件  速率 ▾   循环              停止  │  ← 纯文字
└──────────────────────────────────────────────┘
```

### 3.1 源栏折叠

- **打开片源后**收成一行：文件名/URL 摘要 + 规格 + 「换源」。
- 点击摘要或「换源」→ 展开回完整输入区（本地选择 + URL 输入框）。
- 目的单纯是**省高度给仪表带**；源信息在播放期间是只读语境，不需要常驻输入框。

### 3.2 画面区 chip

- 内容：`解码路径 · codec · 分辨率帧率`，例 `SW · h264 · 1080p30`、`HW · hevc · 720p60`。
- HW/SW 用字样区分（不只靠颜色，保证灰度截图可判读），沿用第一版规则。
- **理由见教训 A**：读数必须与素材规格同屏，否则数字不可比。

### 3.3 常驻仪表带（本次核心）

两行八格，**选取标准是"异常时会先动的量"**：

| 位置 | 仪表 | 数据源 | 异常语义 |
|------|------|--------|----------|
| 主行 1 | **帧率** 实际/名义 | `PlayerStats` | 掉帧率的第一现场 |
| 主行 2 | **丢帧(迟到)** | `dropLate` | late 才是问题，其余三类不混入本格 |
| 主行 3 | **A/V** 偏移 | `avOffsetMs` | 音画不同步 |
| 主行 4 | **CPU** | 资源采样 | 过载/降频 |
| 次行 1 | **启播** 总耗时 | 启播 trace | 起播回归 |
| 次行 2 | **同步余量** | 稳态直方图 | 逼近 0 即将掉帧 |
| 次行 3 | **队列 音/视** | `audioQueue`/`videoQueue` | 供给侧饥饿或堆积 |
| 次行 4 | **缓冲** 水位 | `bufferedMs` | 网络源卡顿前兆 |

显示规则：

- **颜色 + 数值双编码**，灰度截图下仅凭数值也能判读（沿用第一版的"状态不只靠颜色"）。
- **三态显示是硬性要求**（继承 perf-metrics 关键约束 10）：
  `null` → `--`；负数原样显示并标红；正常值正常显示。
  **禁止**用 `optDouble(key, -1.0)` 之类的默认值把 `null` 兜掉 ——
  那等于在展示层重新制造采集层刚消除的状态混淆。
- **丢帧格只显示 late 一类**，不显示四类之和：`overflow` 出现即 bug、`stale` 正常、
  `seekCatchup` 非缺陷，四者语义不同不能相加（继承 perf-metrics 步骤9a 的结论）。
- 刷新节奏搭既有 500ms 进度 tick，**不另开定时器**（避免测试台自身干扰 CPU 读数）。

### 3.4 进度行

- 播放/暂停缩为 **26px 圆钮，内嵌于进度行左侧**。
- 保留双层进度条（播放进度 + 缓冲水位）与时间码（等宽 tabular nums 不抖动）。
- 省掉整整一行全宽按钮的高度。

### 3.5 面板入口

- 四等宽描边框：**性能 / 轨道 / 字幕 / 跳转**（顺序即优先级）。
- 样式完全一致，高度约为原来一半。

### 3.6 次要控件

- `速率 ▾`（点开弹出六档，不再占一整行分段控件）、`循环`、`停止`。
- 纯文字无框；`停止` 靠右且用危险色**字色**。

## 4. 仪表格子可点：一次点击完成"发现异常 → 定位细节"

这是用户明确追加、**必须实现**的一条。仪表格子本身可点，直接跳到解释它的那一页。

| 仪表格 | 落点 |
|--------|------|
| 帧率 / 丢帧(迟到) | 稳态页 · 丢帧构成 + 上屏间隔 |
| A/V · 同步余量 | 稳态页 · 分位数表 |
| CPU | 资源页 · 线程分布 |
| 启播 | 启播页 · 瀑布图 |
| 队列 · 缓冲 | 稳态页 · 队列水位 |

实现要点：

- `DiagnosticsSheet` 需新增**"打开时定位到某页"的入口参数**（当前 `currentTab` 硬编码为 `"概览"`）。
  页名沿用既有六分页：`概览 / 启播 / Seek / 稳态 / 资源 / 日志`。
- **本期只做到"打开面板并落在正确的分页"**。
  "自动滚到对应行并高亮"列为后续增强 —— 先把跳转做了收益最大。

## 5. 横屏沉浸

- 控件 3 秒无操作自动隐藏（沿用第一版）。
- **但 chip 与左下性能 HUD 常驻**：回归时最需要的就是一边看画面一边看数，
  **读数不能跟着控件一起消失**。
- 字幕随控件显隐避让的逻辑保持不变。

## 6. 涉及模块

| 文件 | 改动性质 |
|------|----------|
| `app/src/main/res/layout/activity_console.xml` | 重构（三层控件区 + 进度行内嵌播放键 + 仪表带容器） |
| `app/src/main/java/com/example/lzplayer/console/ConsoleActivity.kt` | 仪表带绑定与刷新、源栏折叠、横屏沉浸调整、跳转分发 |
| `app/src/main/java/com/example/lzplayer/console/DiagnosticsSheet.kt` | 新增"打开时定位到某页"入口参数 |
| `app/src/main/res/values/console_*.xml` | 可能新增仪表格样式与尺寸 token |

**不碰 native**：本 feature 的全部数据源（`getStatsJson` / `getStartupTrace` / 四类丢帧计数）
已由 perf-metrics 步骤1/2/9a 提供，纯消费不新增采集点。

## 7. 风险与依赖

1. **数据源依赖 perf-metrics**：仪表带八项全部消费 `PlayerStats` / 启播 trace /
   稳态直方图。perf-metrics 第一梯队五项中 9a 已完成，9b~9e 尚在队列中；
   **本 feature 只用已落地的字段**，未落地的格子按三态规则显示 `--`，不阻塞。
2. **文件冲突面大**（最主要风险）：`ConsoleActivity.kt` / `DiagnosticsSheet.kt` /
   `activity_console.xml` 三个文件同时被三个 feature 触碰：
   - **test-console-ui 步骤8（未收口）** —— 真机自测尚未做，其验收对象就是这三个文件的旧形态。
     本 feature 一旦重构主界面，步骤8 的 A 屏与 D 屏核对标准即作废，需按新布局重写核对项。
   - **perf-metrics 步骤5 剩余项** —— Seek 页仍在等步骤3 接通，会继续改 `DiagnosticsSheet.kt`。
     本 feature 只在该文件新增入口参数，尽量不动分页内部实现，降低冲突面。
3. **开工前置：工作区两处已验证但未提交的改动必须先提交。**
   当前 `ConsoleActivity.kt` / `DiagnosticsSheet.kt` 处于 modified 状态，内容为
   perf-metrics 步骤5 剩余项 1、2：
   - 性能面板全屏拖动（`isFitToContents=false` + `expandedOffset=0`）；
   - 清除每 tick 写 perf 文件的临时脚手架 —— 那个 `writeText` **先截断再写**，
     调试 stop→play 时已读到空文件并**误导过一次**。
   不先提交，本 feature 的大规模重构会把它们埋进同一堆 diff 里，**后续归因困难**。
4. **仪表带占高与小屏适配**：两行八格在小屏或 4:3 素材下可能挤压画面区。
   验收时需在实际设备上确认画面区未被压到不可判读。
5. **刷新开销**：八格 + chip 每 500ms 刷新，必须只更新变化项、不重建 View，
   避免测试台自身把 CPU 读数带偏（第一版风险 7 的延续）。

## 8. 验收标准（整体）

1. 竖屏主屏无需打开任何面板即可回答"现在健康吗"：八项读数常驻可读。
2. 三层视觉语言各自唯一，同层内无样式例外（约束 1）。
3. 优先级表达中不出现"专属颜色/专属尺寸"（约束 2）。
4. 任一仪表格点击 → 一次点击落到指定分页（第 4 节映射表逐项核对）。
5. 横屏 3s 后控件隐去，chip 与 HUD 仍在。
6. 灰度截图下八项读数与 HW/SW 仍可判读。
7. 所有读数遵守三态规则，无 `-1` 冒充"没采到"。
