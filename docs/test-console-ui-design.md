# LZPlayer 测试台 UI 设计文档（test-console-ui）

> 创建日期: 2026-08-08
> 修订: 2026-08-08 —— 新增第 3.C 节「性能面板」（原「诊断面板」升级）、第 3.F 节「基准序列」、
> 第 5 节「指标目录与采集点」。起因：原设计只有八项瞬时读数，能告诉你"慢"，
> 不能告诉你"慢在哪一段"，无法支撑针对性优化。
> 实施计划: ../features/test-console-ui/plan.md、../features/perf-metrics/plan.md

## 1. 背景与目标

### 背景

high-perf-player 六个阶段（Phase 0~5）的 native 代码已全部完成，待真机回归。这轮演进带来了大量新能力：

- Phase 1：变速播放（0.5x~2.0x，音调不变）、精准 seek 提速
- Phase 2：MediaCodec 硬解 + Surface 零拷贝、软解 fallback（`VE_INFO_DECODER_FALLBACK`）
- Phase 3：网络源（HTTP/HTTPS）、三水位缓冲与 `BUFFERING_START/UPDATE/END` 事件
- Phase 4：AAudio/OpenSL ES 双音频后端、调度精修
- Phase 5：多音轨切换、字幕轨切换/关闭、外挂字幕、`ON_SUBTITLE`/`ON_SUBTITLE_CLEAR`

而 app 模块的 UI 仍停留在旧版：仅有「选择文件 / 播放 / 暂停 / 停止 / 进度条 / SurfaceView」，单个 `MainActivity.java`。新增能力**在界面上完全不可达**，也**无处读出内部状态**，导致：

1. 新能力无法手工触发，回归只能靠 logcat 反推；
2. 真机回归缺少统一的操作载体，lzplayer-test-expert 的用例难以稳定复现；
3. 关键指标（解码路径、音视频偏移、丢帧、队列深度）不可见，性能问题定位靠猜。

### 目标

做一个**工程测试台**界面，不是消费级播放器。判定标准只有一条：

> **每一项已实现的能力，都有一个可以按到的控件；每一项内部状态，都有一处当场可读的读数。**

同时这个界面本身就是真机回归的操作载体——lzplayer-test-expert 的用例直接以它为 UI 入口，截图即证据。

### 非目标

- 不做消费级播放体验（手势调音量/亮度、播放列表、历史记录、缩略图预览等一概不做）
- 不做视频轨切换（native 本期不支持，UI 上只读并灰掉）
- 不做美观优先的动效；一切服从"读数可信、状态可辨"

## 2. 设计语言

设计稿已以 Artifact 形式产出，本节概述其规则，实施时以此为准。

### 定位隐喻：视频测试仪器

界面参照广播级视频测试仪器（波形监视器 / 矢量示波器）的观感，而非流媒体 App：

- **SMPTE 彩条**作为结构分隔元素（区块之间的分隔条），既是视觉锚点也是色彩参考
- **等宽字体**承担全部标签与读数；数字启用 tabular nums（等宽数字），保证读数跳动时字符不横向抖动
- 布局密度偏高，信息优先于留白

### 色彩

主色与语义色**严格分家**，避免"主色即成功色"的歧义：

| 角色 | 色值 | 说明 |
|------|------|------|
| 主色 | `#3FA9C4` | 去饱和 SMPTE 青，用于强调、选中态、主按钮 |
| ok | `#52B788` | 正常/成功/激活 |
| warn | `#D9A441` | 警告（软解回退、缓冲中、偏移偏大） |
| crit | `#E5544B` | 错误/危险 |
| 底色 | `#0E1217` | 页面背景 |
| 面板 | `#171C23` | 卡片/面板背景 |
| 发丝线 | `#272E38` | 1px 分隔线、边框 |
| 正文 | `#D3DAE4` | 主要文字 |
| 弱化 | `#8792A2` | 次要文字、标签 |

轨道条纹沿用剪辑软件约定，便于一眼区分轨道类型：

| 轨道 | 色值 |
|------|------|
| 视频 | `#4A7FD4` |
| 音频 | `#52B788` |
| 字幕 | `#D9A441` |

### 无障碍原则：状态不只靠颜色

灰度截图（以及色觉障碍用户）下同样必须可读，因此每个状态都有**形状或文字**冗余：

- 硬解/软解：显示 `HW` / `SW` 字样，不只是绿/黄
- 缓冲中：出遮罩层 + 百分比数字，不只是变色
- 错误：带独立标识符（`ERR` 前缀 + 错误码），不只是红字

这条规则同时服务于回归测试——截图是灰度或压缩后仍可判读。

## 3. 屏幕设计（四块）

### A. 主控台（竖屏主界面）

自上而下：

1. **源栏**：两种输入方式并列
   - 本地路径：走 MediaSelector 选文件
   - 网络 URL：文本输入框 + 载入按钮
2. **SurfaceView 视频区**：固定宽高比容器
3. **常驻 HUD**（叠在视频区上）
   - 左上：解码路径 `HW`/`SW` + codec 名（如 `HW h264`）
   - 右上：状态机状态（IDLE/PREPARED/STARTED/PAUSED/...）+ 当前速率（如 `1.25x`）
   - **性能 HUD（2026-08-08 新增，可开关）**：左下角三行等宽小字，
     不打开面板也能盯住关键指标，便于一边操作一边观察：
     ```
     24.0fps  drop 0
     A/V +9ms  buf 1002ms
     cpu 12.4%  first 264ms
     ```
     默认关闭（避免遮挡画面影响色彩/画幅核对），由四宫格入口旁的小开关切换；
     横屏沉浸态下与原 HUD 一同常驻。刷新节奏搭既有进度 tick，不另开定时器。
     > **2026-08-08 修订（适用范围收窄）**：「不另开定时器」**只约束 HUD**。
     > HUD 常驻在画面上、且只显示瞬时值，搭进度 tick 即可。
     > **性能面板另有自己的 1 秒采样节拍**（见 3.C 与 5.4）——CPU 占用必须两次采样求差，
     > 而暂停/播完后进度回调就停了，只搭进度 tick 会让 CPU 永远停在"首次采样"。
4. **字幕 overlay**：叠在视频区下部，带描边文本
5. **双层进度条 + 时间码**
   - 底层：已下载/已缓冲进度（网络源）
   - 上层：已播放进度
   - 右侧时间码 `当前 / 总时长`，等宽数字
6. **传输控件**：播放暂停（合一）/ 停止 / 循环开关
7. **速率分段控件**：0.5 / 0.75 / 1.0 / 1.25 / 1.5 / 2.0 六档
8. **四宫格入口**：轨道 / 字幕 / 跳转 / 诊断

### B. 轨道面板（BottomSheet）

- **视频轨**：只读列表并灰掉，标注"本期不支持切换"
- **音频轨**：单选列表，每项显示 语言 / codec / 采样率 / 声道
- **字幕轨**：单选列表，第一项固定为「关闭」
- **加载外挂字幕**：按钮，选文件后调 `addExternalSubtitle`
- **切轨耗时**：切换完成（收到 `ON_TRACK_CHANGED`）后在该项原位显示耗时毫秒数，用于对照验收线「硬解切轨 < 200ms」

### C. 性能面板（全高 BottomSheet，六个分页）

> 2026-08-08 修订：原「诊断面板」只有八项瞬时读数，回答不了"这 800ms 花在哪"。
> 现升级为分页面板，**每一页对应一类可优化对象**。

**面板刷新节拍（2026-08-08 实施时明确）**：面板**自带一个 1 秒 ticker**，
`setOnShowListener` 起、`setOnDismissListener` 停，**只在面板显示期间运行**。
这与 5.4「采样只在性能面板打开或跑分期间进行」一致；3.A.3 那句"不另开定时器"只约束 HUD。
理由：CPU 占用要两次采样求差，暂停/播完后进度回调停发，搭进度 tick 会让 CPU 永远显示"首次采样"。

**面板文案一律纯文本**：读数与提示都是 `TextView`，**不解析 Markdown**。
不要在文案里写 `**强调**` 之类的标记，星号会原样显示在界面上。
需要强调用词序、括号或独立成行解决。

**尚未接通的页不留空白**：某项数据源还没做时，该页必须明写"尚未接通（<feature> 步骤N）"
并列出接通后会显示什么。空白页会被当成功能坏了。

面板改为可拖到全屏高度（`BottomSheetBehavior` 的 expanded 态），顶部一行分页 tab，
tab 间用 SMPTE 彩条细条分隔。分页刻意按"优化对象"而非"数据类型"划分——
打开一页就应该知道要动哪段代码。

```
┌──────────────────────────────────────────┐
│ ▬▬▬▬▬▬  性能            [跑分] [导出] │  ← 彩条 + 标题 + 动作
├──────────────────────────────────────────┤
│ 概览 │ 启播 │ Seek │ 稳态 │ 资源 │ 日志 │  ← 分页
├──────────────────────────────────────────┤
│                                          │
│              (分页内容)                   │
│                                          │
└──────────────────────────────────────────┘
```

#### C1. 概览页

一屏之内回答"这次播放健康吗"。上半是四个**大字读数**（比其他页字号大一档，
供截图时远距离判读），下半是原有八项读数的紧凑栅格 + 三个策略开关。

四个大字读数选取标准：**用户可感知 + 一眼判好坏**。

| 读数 | 判定线 | 颜色语义 |
|------|--------|----------|
| 启播总耗时 | < 500ms 良 / < 1000ms 可 / 更高警告 | ok / warn / crit |
| 实际帧率 vs 名义帧率 | 偏差 < 2% | 偏差越大越警告 |
| 丢帧率 | 0 为 ok，> 1% 警告 | — |
| 进程 CPU | < 15%（单核归一）良 | — |

策略开关三个（强制软解 / 强制 OpenSL ES / Vulkan 渲染），保留原设计的
"下次 prepare 生效"常驻说明。Vulkan 那个额外注明"需同时强制软解"，
因为硬解直出 Surface 不经过任何渲染器，单开它没有任何观感变化。

#### C2. 启播页 —— 瀑布图

**这是本次修订的核心。** 启播是一条串行链路，只有把它拆开才知道该优化谁。
用水平堆叠条（瀑布图）呈现，每段一个颜色，段内标注毫秒数；段太窄放不下文字时
数字移到条外侧，**绝不省略**。

```
启播总耗时  231.2ms          源: local · HW h264 · 1920×1080 30fps 20Mbps
├┬─────────────────────────────────────┬┬──────────────────────┬┤
││          解析流信息 145.0           ││     首帧解码 79.6    ││
├┴─────────────────────────────────────┴┴──────────────────────┴┤
 ↑                                      ↑                       ↑
 打开 5.2                         建链 0.7               首帧上屏 0.7
 T0                                   T3 T4/T5                  T7

  ┄┄ 叠加区间 ┄┄  解码器 configure 66.3ms（落在 T5→T7 首帧窗口内）

  打开容器        5.2ms   avformat_open_input
  解析流信息    145.0ms   avformat_find_stream_info      ← 最大项 (63%)
  建链            0.7ms   接线耗时(渲染器/looper)；configure 不在此段内
  首帧解码       79.6ms   T5→T6 第一帧解出
  首帧上屏        0.7ms   T6→T7 交给 SurfaceFlinger
  ─────────────────────────────────────────
  分段之和      231.2ms   与总耗时一致（误差 < 5ms 即采集点完整）
  首帧耗时       80.3ms   T5→T7（start 到看见画面）
  首声耗时          —     T5→T8（本轮未单独记录）
```

> **示例数字来自真机：OPPO PHK110 / Android 16 + 1920×1080 h264 20Mbps 30fps
> 硬解路径（素材 `VID_20230814_205835.mp4`）。换设备或换素材会有显著差异**——
> 数量级和**分段排序**都会变，不要把这组数字当成任何形式的目标值或参考线。
> 同一素材的软解路径对照：打开 5.0 / 解析 133.8 / 建链 0.7 / configure 0.5 /
> 首帧解码 49.6 / 首帧上屏 57.2 / **总耗时 246.4ms**。
>
> 这组数字取代了本节早期一份凭空构造的示例（打开 118 / 解析 42 / 建链 386 /
> configure 341 / 首帧 264、总 842ms）。那份示例把「建链」画成最大项、
> 「解析流信息」画成可忽略的小项，**与真机情况恰好相反**，会把看设计稿的人
> 引向错误的优化方向，故整体替换。详见 `startup-cpu-opt-design.md` §0。

> **实测修正（2026-08-08，步骤1 打点后）**：上面示意图把「解码器 configure」
> 画成建链段的子项，这是错的。解码器的 `prepare` 是异步的（投消息进自己的
> looper），`continuePrepare` 在 configure 真正执行之前就返回了，因此
> **T3→T4「建链」只是接线耗时**（真机实测 0.4~2.7ms），而 configure 那几十到
> 几百毫秒落在 `start` 之后的首帧窗口里。
>
> 所以 configure 必须作为一条**跨段的叠加区间**呈现（它自带 t4aBegin/t4aEnd
> 两个绝对位置），不能和任何分段做减法——早先按 `建链 − configure` 计算
> 「建链其余部分」，直接得到负数。JSON 里对应
> `decoderConfigureMs` + `configureOverlapsFirstFrame` 两个字段。
>
> 真机首批数据（OPPO PHK110 / Android 16 / **640×360 h264 合成片** / 无音轨）：
>
> | | 打开 | 解析 | 建链 | configure | 首帧解码 | 首帧上屏 | 总计 |
> |---|---|---|---|---|---|---|---|
> | 硬解 | 10.0 | 2.4 | 2.7 | 80.9（叠加） | 85.9 | 0.7 | **101.7** |
> | 软解 | 4.7 | 2.1 | 0.4 | 0.4 | 2.4 | 2.1 | **11.8** |
>
> **⚠ 这组数据是用 ffmpeg 造的 640×360 合成小素材测的，仅用于验证采集点完整性
> （分段之和自洽、无负值、双路径都有值），不可作为性能基线。**
> 当时据此得出的"硬解起播比软解慢约 8.6 倍、瓶颈是 MediaCodec configure"
> **已被 1080p 真实素材推翻**：真机上软硬解总耗时基本持平（246.4 / 231.2ms），
> 第一大项是**解析流信息**（133.8 / 145.0ms，在这份小素材上只有 2.1 / 2.4ms，完全不可见）。
> 见 `startup-cpu-opt-design.md` §0 与 §1。
>
> 保留这组数字的意义只剩一条：它证明拆解分段本身是有效的——
> 总耗时单看一个数字不会指向任何具体的段。

设计要点：

- **最大项高亮**：自动给耗时占比最大的段加主色描边并标 `←`，省去人工比对。
- **T 编号常驻**：与第 5 节的采集点表一一对应，看到某段异常能直接定位到代码位置。
- **首帧拆两段**：`T5→T6`（解码）与 `T6→T7`（等时钟）区分开。这两者的优化方向
  完全相反——前者要加快解码或降低首帧依赖，后者说明画面已就绪只是在等音频/时钟，
  该动的是起播锚点策略。合成一个数字会把人引向错误的方向（这正是先前
  "起播 0.6s 追平"议题里踩过的坑）。
- **历史对照**：同一源最近 5 次启播的总耗时列成小柱状图，用于判断抖动还是趋势。
  优化前后对比就靠这个，不必每次翻日志。

#### C3. Seek 页

seek 是第二条值得拆解的串行链路，且它有**精度**这个独立维度。
最近 10 次 seek 列表，每行一次：

```
  #  目标      总耗时   暂停  定位  预热   首帧    精度
  1  00:32.500   214ms   12   118    84   +18ms   -12ms
  2  00:05.000   186ms    9    96    81   +15ms    +4ms
  3  01:12.000   902ms   11   771   120   +22ms   -35ms  ← 慢
```

- **三阶段分解** 对应 native 的 `SEEK_STAGE_PAUSING / SEEKING / PRIMING`，
  定位段偏大通常是关键帧间距或 demux 回溯的问题，预热段偏大是解码追帧的问题。
- **精度** = 首帧实际 pts − 请求位置。这一列直接验"精准 seek"能力，
  正负号有意义（负=落在请求点之前）。
- 底部给 p50 / p95 / max 三个统计，单次数据不足以判定回归。

#### C4. 稳态页 —— 趋势与分布

稳态问题是统计性的，瞬时值会骗人，因此这一页以**曲线和分位数**为主。

```
帧率   24.0 / 24.0 fps        ▁▂▃▃▂▃▃▃▂▃▃▃▂▃▃  (60s)
A/V    +9ms  峰值 +23ms       ──▂▁─▁▂▁──▁▁▂▁─   零线居中
丢帧   0 / 252  (0.00%)

  解码耗时 ms      p50    p95    max
    视频            4.2    9.8   18.1
    音频            0.6    1.1    2.4
  上屏耗时 ms       1.8    3.1    6.9
  同步余量 ms      28.4   11.2    0.4   ← 越小越接近丢帧

  队列水位        当前   峰值   上限
    音频包          47     64    120
    视频包          28     41    120
    帧队列           3      6     12
  缓冲水位      1002ms
```

- **同步余量**（每帧渲染前距其应显示时刻还剩多久）是丢帧的**前兆指标**。
  丢帧率还是 0 但余量 p95 已逼近 0，说明再多一点负载就会开始掉帧——
  这是丢帧计数给不出的预警。
- 火花线用 60 秒滑动窗口，A/V 偏移那条**零线居中**，正负偏移方向一眼可辨。

#### C5. 资源页

直接服务于最初那条"CPU 占用率不高"的目标。**按线程拆**，否则只知道总量高、
不知道该优化哪一环。

```
  进程 CPU   12.4%  (单核归一)     ▂▃▂▂▃▂▂▃▂
  RSS       184 MB    Native heap  96 MB

  线程                CPU%    说明
    vdec_thread        6.1    视频解码
    audio_render       2.2    音频渲染 + 变速
    adec_thread        1.8    音频解码
    video_render       1.4    上屏
    demux_thread       0.6    解封装
    player             0.3    命令面
```

线程名与 native 侧 `ALooper::setName()` 设的名字一致，读数能直接对应到某个组件。
采样区间固定 1 秒，面板打开时才采（不打开不采，避免测量本身影响被测对象）。

#### C6. 日志页

原「事件流」下沉为一页，行为不变：按时间倒序、事件名与 `VEDef.h` 常量同名、
可与 logcat 逐条对照。

**导出**升级为导出**整份报告**（见 3.F），不再只是事件流。

### D. 横屏沉浸

- 控件 3 秒无操作自动隐藏，HUD **常驻**（回归时随时能读解码路径与状态）
- 字幕在控件浮出时上移，避免被传输控件遮挡
- 用途：验证旋转处理、色彩量程（Phase 0.A 的 limited/full range + BT.601/709 修正）、字幕遮挡

### F. 基准序列（一键跑分）

2026-08-08 新增。**针对性优化的前提是可复现的对照**——手工点几下得到的数字
受操作节奏影响，改一行代码后无法判断变化是真实收益还是抖动。因此在性能面板
标题栏放一个「跑分」按钮，跑一段固定动作序列并产出一份报告。

序列（全自动，约 60 秒）：

| 步 | 动作 | 采集 |
|----|------|------|
| 1 | 冷启动打开当前源 → 起播 | 启播瀑布全项 |
| 2 | 稳态播放 15s | 帧率/丢帧/解码耗时/CPU/线程 CPU |
| 3 | seek 到 5 个固定位置（10%/50%/90%/0%/75%） | 每次的三阶段 + 首帧 + 精度 |
| 4 | 依次切 0.5x / 1.0x / 2.0x，各播 5s | 生效耗时、变速下 A/V 偏移 |
| 5 | 音轨切换（若多轨）、字幕开关 | 切轨耗时 |
| 6 | seek 到末尾附近播至 EOS | EOS 是否按两条链路正确收尾 |

设计约束：

- 位置用**百分比**而非绝对秒数，保证换素材后仍可对照。
- 每步之间插入固定 1s 静默，避免上一步的尾流污染下一步读数。
- 跑分期间禁用其它交互并显示进度，防止误操作污染数据。
- 报告落 `/sdcard/Android/data/<pkg>/files/perf/<时间戳>-<素材名>.txt`，
  同时写一份 `.json` 便于脚本 diff。**文本版给人看，JSON 版给回归脚本看**，
  两份内容必须同源，避免出现"报告好看但脚本判失败"的分裂。
- 报告头部记录环境指纹：机型、Android 版本、素材（分辨率/编码/帧率/时长）、
  三个策略开关状态、渲染后端、音频后端。**缺了这些的报告不能用于对照**，
  因为硬解/软解、AAudio/SLES 的数字根本不在同一量级。

`lzplayer-test-expert` 的用例后续可直接以这个序列为骨架，
把"手工点一遍 + 看 logcat"换成"跑一次 + diff 报告"。

### 诊断数据源（2026-08-08 核对工作区代码后修订）

初稿假设诊断读数与策略开关都缺 native 接口，实际核对后**大部分已具备**：

- `VEPlayer.getStats()` → `PlayerStats`，字段：`state / decoder / codec / audioBackend / avOffsetMs / renderedFrames / droppedFrames / audioQueue / videoQueue / bufferedMs / source / speed / buffering / positionMs / durationMs`。JNI `nativeGetStats` → `VEPlayer::getStats()` 已实现，**拉模式**，UI 按进度 tick 取用即可，不必新增 native 定时器。诊断面板八项读数由此全部有真实来源。
- `VEPlayer.setForceSoftwareDecoder(boolean)` / `setForceSlesAudio(boolean)` 已透出 JNI/Java，语义为**下次 prepare 建链生效**。

### 仍需新增的 native 改动（前置子任务）

**轨道 JSON 字段补齐**：`VEPlayer::getTrackInfoJson()` 目前只输出 `index/type/lang/title/codec/active`，缺轨道面板要显示的**采样率与声道数**——`VETrackInfo` 内部已有 `sampleRate`/`channels`（`VEDemux.cpp` 填充），只是没序列化。需补 JSON 字段并扩展 `TrackInfo.java` 解析。codec 名可在 Java 侧由 `codecId` 映射兜底。

### app 模块现状与语言选择

- 现状：`app/src/main/java/com/example/lzplayer/MainActivity.java`，单 Activity + `activity_main.xml`，Java。
- CLAUDE.md 要求新 UI 代码优先 Kotlin。**本 feature 新增界面代码一律用 Kotlin**。
- 与既有 `MainActivity.java` 是共存（新增 `TestConsoleActivity`，旧的保留作对照）还是直接替换，**由实施时决定并在 plan/status 中记录**。倾向先共存，回归通过后再决定是否删旧。

## 5. 指标目录与采集点（2026-08-08 新增）

本节是实施依据，也是**数字含义的唯一定义处**。任何读数出现争议，以此为准。

> **⚠ 本节及 3.C2 中出现的 640×360 数据（打开 10.0 / 解析 2.4 / 建链 2.7 /
> configure 80.9 / 首帧解码 85.9 / 首帧上屏 0.7 / 总计 101.7 等）
> 全部来自 ffmpeg 造的合成小素材，仅用于验证采集点完整性
> （九个点是否都有值、分段之和是否自洽、软硬解两路是否都覆盖到），
> 不可作为性能基线。**
>
> 原因：合成小素材会**系统性单向掩盖**与数据量成正比的瓶颈——
> 容器探测、解码、纹理上传、内存。换成 1920×1080 20Mbps 真实素材后，
> 「解析流信息」由 2~4ms 变成 133~145ms，**跃升为启播第一大项**，
> 瓶颈排序整体改变。
>
> **性能基线一律以 `startup-cpu-opt-design.md` §1 的 1080p 实测数据为准**，
> 且任何测量都必须记录素材指纹（分辨率/编码/帧率/码率/时长/有无音轨），
> 跨素材的数字比较必须显式标注不可比。

### 5.1 时间基准

全部时间戳统一用 `std::chrono::steady_clock`（native）与 `SystemClock.elapsedRealtimeNanos()`
（Java），**不用 wall clock**——后者会被系统时间调整或 NTP 校准打乱，
在跑分这种依赖差值的场景里会产出负数耗时。

跨语言的段（如 T0 由 Java 侧发起）以 native 侧记录为准，Java 只负责把
"我什么时候调的"作为 T0 传下去，避免两个时钟源相减。

### 5.2 启播里程碑

| 编号 | 含义 | 采集位置 |
|------|------|----------|
| T0 | 收到打开请求 | `VEPlayer::onPrepare` 入口（Java 侧调用时刻由参数传入） |
| T1 | 容器打开完成 | `VEDemux::openInput` 返回后 |
| T2 | 流信息解析完成 | `avformat_find_stream_info` 返回后 |
| T3 | 轨道表就绪 / PREPARE_DONE 上报 | `VEDemux::buildTrackList` 返回后 |
| T4 | 建链完成（PREPARED） | `VEPlayer::continuePrepare` 返回前 |
| T4a | 解码器 configure 完成 | 硬解 `VEMediaCodecVideoDecoder::configureCodec` 末尾；软解 `VEVideoDecoder::prepare` 末尾 |
| T5 | start 生效 | `VEPlayer::onStart` 入口 |
| T6 | 首帧解出 | 视频解码器产出第一个 `VEFrame` 处 |
| T7 | 首帧上屏 | **就地打点**：软解在 `VEVideoDisplay::onRender` 的 `renderFrame` 返回后，硬解在 `releaseOutputBuffer(render=true)` 后 |

> **T7 不能复用 `FIRST_FRAME` 事件**（2026-08-08 实施步骤1 时核实并纠正）。
> 该事件只在 seek 路径上报——`m_NotifyFirstFrame` / `mNotifyFirstFrame` 仅由
> `onSeekTo` / `onSeek` 置真，起播时始终为假；而 `VEPlayer` 收到 FIRST_FRAME 后
> 还会主动忽略非 `SEEK_STAGE_PRIMING` 的那些。也**不要为启播新发这个事件**：
> 它已透到 Java 的 `VE_PLAYER_NOTIFY_EVENT_ON_FIRST_FRAME`，改语义会影响 app 行为。
| T8 | 首个音频帧进设备 | `VEAudioRender::anchorClock` 首次调用处 |

派生量：打开=T2−T0，建链=T4−T3，首帧=T7−T5，首声=T8−T5。

**启播总耗时 = (T4−T0) + (T7−T5)**，即"就绪耗时 + 首帧耗时"，
**刻意排除 T4→T5**：非自动起播时那段是用户的思考时间，算进去会让这个数字失去意义
（它单独作为 `startGapMs` 列出）。纯音频文件没有 T6/T7，总耗时退化为
(T4−T0) + (T8−T5)，由 `totalBasis` 字段标明是 `video` 还是 `audio` 基准——
否则这类文件永远拿不到总耗时。

分段之和的自洽性因此按基准分别成立：video 基准下
`queueWait+open+streamInfo+trackList+buildChain+firstFrameDecode+firstFramePresent`
等于总耗时；audio 基准下末两项换成 `firstSound`。真机实测误差 0.00~0.10ms
（0.1 来自一位小数的舍入）。

另：`decodePath` 只在确实有视频轨时才填。纯音频文件的 `mVideoHardware` 恒为
false，若无条件上报会变成 `software`，看报告的人会以为它跑了软解视频并拿它
和真正的软解数据对比——这类文件一律输出 `-`。

注意 T7 的两个采集点物理含义略有差别：软解是"提交给 GLES/Vulkan 并 swap"，
硬解是"交给 SurfaceFlinger 合成"。两者都不等于像素真正点亮，
**因此硬解与软解的首帧耗时不可直接互比**，这条要写进报告脚注。

### 5.3 稳态指标

| 指标 | 定义 | 采集位置 |
|------|------|----------|
| 实际帧率 | 60s 滑动窗口内上屏帧数 / 窗口时长 | 复用已有 `renderedFrames` 计数，UI 侧差分 |
| 名义帧率 | 容器标注 fps | 已有 `VEMediaInfo::fps()` |
| 丢帧率 | dropped / (rendered + dropped) | 已有两个计数器 |
| A/V 偏移 | 视频帧 pts − 主时钟，带符号 | 已有 `avOffsetMs` |
| 解码耗时 | 单帧 `avcodec_send/receive` 或 MediaCodec dequeue 往返耗时 | **需新增**：解码器内打点，累积成直方图 |
| 上屏耗时 | `renderFrame` 入口到返回 | **需新增**：渲染器内打点 |
| 同步余量 | 帧应显示时刻 − 实际提交时刻 | **需新增**：`VEAVsync` 计算等待时已有该差值，只需留存 |
| 队列水位 | 音/视包队列、帧队列的当前值与峰值 | 已有 `getQueueDepth`，峰值需新增 |

分位数（p50/p95/max）在 **native 侧**用固定桶宽直方图累积，不回传原始样本——
每帧一条样本按 60fps 算一分钟就是 3600 条，跨 JNI 传输本身就会影响被测对象。

### 5.4 资源指标

| 指标 | 来源 | 说明 |
|------|------|------|
| 进程 CPU% | `/proc/self/stat` 的 utime+stime 差分 ÷ 采样墙钟 | 归一到单核；除以核数得整机占比，两者都显示避免误读 |
| 线程 CPU% | `/proc/self/task/<tid>/stat` 同法 | 线程名取自 `/proc/self/task/<tid>/comm`，与 `ALooper::setName()` 对应 |
| RSS | `/proc/self/statm` 第二项 × 页大小 | — |
| Native heap | `Debug.getNativeHeapAllocatedSize()` | Java 侧可直接取 |

全部在 **Java 侧**读取即可，不需要 native 改动。采样只在性能面板打开或跑分期间进行。

### 5.5 传输方式

新增指标一律走**已有的拉模式**：扩展 `VEPlayer::getStatsJson()` 的输出，
Java 侧 `PlayerStats` 增加对应字段。**不新增回调通道**——CLAUDE.md 要求
事件走 `Native → NativeLib.EventHandler → IVEPlayerListener` 这一条链路，
而这些是数值快照不是事件，塞进事件流只会把日志页冲垮。

启播里程碑与 seek 记录属于"一次性结构化数据"，用两个独立的 getter
返回 JSON（`getStartupTraceJson()` / `getSeekTraceJson()`），
避免把它们混进每 tick 都要解析的 stats 里造成无谓开销。

## 6. 验收标准

1. Phase 0~5 的每项能力在 UI 上都有可按到的控件（逐项对照 high-perf-player 的六阶段能力清单）
2. 诊断面板八项读数全部有真实数据来源，无占位假数据
3. 四块屏幕在真机上截图核对通过，灰度下状态仍可判读
4. 切轨耗时读数可用于判定「硬解 < 200ms」验收线
5. 事件流列表的事件名与 `VEDef.h` 常量逐条对得上

性能面板部分（2026-08-08 追加）：

6. 启播瀑布图各段之和与「启播总耗时」误差 < 5ms（否则说明有未计入的空隙，
   采集点有漏）
7. 瀑布图能正确指出最大项：人为在某一段插入 200ms 延时，该段应被高亮为最大项
8. seek 页的精度列在已知素材上与 ffprobe 的关键帧位置对得上
9. 同步余量 p95 在正常播放下 > 0；人为加载压力后应先看到余量下降，
   再看到丢帧出现（顺序不能颠倒，否则该指标失去预警意义）
10. 线程 CPU 之和 ≤ 进程 CPU，且线程名与 native 的 looper 名一一对应
11. 跑分报告的 txt 与 json 两份内容一致；报告头部环境指纹完整
12. 同一素材同一配置连续跑分两次，启播总耗时差异 < 15%（否则数据不足以支撑对照）

性能面板部分（2026-08-08 追加）：

| 风险/依赖 | 说明 | 应对 |
|-----------|------|------|
| **测量本身影响被测对象** | 每帧打点 + 跨 JNI 传样本会拖慢解码 | 直方图在 native 侧累积只回传分位数；CPU 采样仅在面板打开/跑分时进行；打点用 steady_clock 不做格式化 |
| 硬解与软解首帧不可比 | 两者 T7 的物理含义不同（见 5.2） | 报告脚注写明；跑分报告头部记录解码路径，禁止跨配置对照 |
| 时钟源混用 | wall clock 会被 NTP 校准打乱产出负耗时 | 统一 steady_clock / elapsedRealtimeNanos，跨语言段以 native 为准 |
| 分位数样本不足 | 刚起播时样本太少，p95 无意义 | 样本数 < 30 时显示 `--` 而不是给出一个假数字 |
| 跑分序列耗时长 | 约 60s，期间不能操作 | 显示进度与剩余时间，允许中断；中断产出的报告标记为「不完整」，不得用于对照 |
| 面板数据量大 | 六页 + 曲线，容易把主线程拖卡 | 曲线用固定长度环形缓冲；只有可见页刷新，切页才重绘 |
