LZPlayer 测试评价系统

一套让播放器能力可测量、可判定、可回归的系统。覆盖 16 个维度，每个维度都有 可复跑脚本与归档基线。

更新 2026-08-28 · 分支 master_openclaw

这套系统解决的不是"跑一遍看看有没有崩"，而是三个更难的问题：怎么知道 某个能力是好的（判定）、怎么知道它比上次好还是坏（回归）、 以及怎么知道测试本身有没有真的测到东西（自检）。 最后一条尤其重要——本文第 6 节列出了五种"看起来通过、实际什么都没测"的形态， 每一种都真实发生过。

01架构总览

分四层：素材、采集、判定、回归。数据单向流动，每层的产物都落盘， 下游只读上游的产物而不重新采集——这样同一份采集可以反复喂给生成器， 得出的必然是同一组数字。

为什么采集与判定分开：如果边跑边判，同一次运行只能得出一个结论， 改判据就得重跑真机。分开之后，判据、口径、阈值都可以离线迭代， 而原始数据不变——这也是"同一份 logcat 反复喂给生成器只能得出同一组数字"这条 口径能够成立的前提。

02采集层：五套 native 埋点

全部由播放器进程自采，经 logcat 输出。每条日志都是固定格式的 key=value，一条 adb logcat | grep 即可提取完整序列。

VESTAT — 逐秒时间线

挂在已有的 kWhatProgressTick 上，不新增周期唤醒源。 累计量一律发差值（本秒新增）：从绝对值求差要求采样无丢失， 而日志恰恰会被配额丢。

字段含义采样时刻
fps本秒实际上屏帧数presentInterval 样本数差值
dropLate迟到丢帧（阈值 100ms，即落后 3 帧才丢）本秒新增
dropOvfcredit 记账失守，出现即 bug本秒新增
dropStaleflush/seek 后的在途旧帧，正常本秒新增
dropSeek精准 seek 追帧丢弃，属 seek 成本本秒新增
vpark / apark解码器 credit 用尽次数，判断上下游瓶颈的关键本秒新增
vstarve / astarve上游饥饿次数本秒新增

"采样时刻"这一列是必需的，不是补充说明。 曾有一个 avOffMs 字段与 syncWorstMs 用同一个函数 getLastDiffUs()，差别只在调用时机——前者在等待期采样，量到的是 "距下一帧上屏还剩多久"，恒为正且随流水线深度变化，与同步质量无关。 该字段已整列删除。同一个量在不同时刻采样，含义可能完全不同。

VERENDER — 渲染开销分解

uploadMs / drawMs / swapMs 三段墙钟，加 threadCpuMs / inCpuMs / gapMs 三个 CPU 量。 三段保持墙钟不变——swap 的墙钟正是等 vsync 的时长，换成 CPU 就把 这个信息毁掉了。gapMs = 线程总 CPU − 插桩区间 CPU，两边都是 CPU 时间才可比。

VEGAUGE — 插桩覆盖率自校验

拿分段之和跟独立测得的线程总量对账。这是整套系统里唯一能自动抓住 "指标漏账"的机制。

环节线程 CPU已插桩缺口
vdec47.8%47.5%0.4%
adec3.6%2.5%1.1%
demux1.7%1.1%0.6%
video_render——0.84 ms/帧

这套机制上线当天就抓到一个真问题：vdec 线程烧 43% CPU 而 instrumented=0.0——插桩只覆盖了 receive_frame， 漏掉由 mDecodeAccumUs 单独累加的 send_packet 段。 补齐后覆盖率从 0% 升到 99%。

VESeekTrace — seek 三阶段

pausing → seeking → priming 三段耗时加精度，环形缓冲保留最近 10 条。 分开看才知道该动哪边：定位段偏大是关键帧间距或 demux 回溯的问题， 预热段偏大是解码器追帧的问题。实测 seek 总耗时的 86~99% 在预热段。

VEStartupTrace — 启播里程碑

T0~T8 分段，含 codec 创建/配置/启动的子拆分。三态语义： null（未采到）/ 负值（采集点顺序颠倒）/ 数值。 配一条硬判据：分段之和与总耗时之差 < 5ms。

03判定层：10 条判据与统计口径

报告生成器 gen-report.py 输出 report.txt 与 report.json，由同一中间结构渲染——否则两份数字会 各自漂移，而读报告的人无从判断哪份可信。

缺交叉校验来源的判据一律标 INCONCLUSIVE， 不许算 PASS。 单一来源的判据不予采纳——这条规则挡住的不是错误的数字，而是 "看起来有结论、实际无从验证"的结论。

统计口径（写死在生成器里，不交给读报告的人）

  1. 所有逐秒列整段统计，给 n/mean/p50/p95/max，禁止只报某一行。 依据：CPU 列单次运行内方差达 30 个百分点，挑几行就能得出相反结论—— 这个错误真实发生过，据 4 行样本得出"软硬解 CPU 基本相同"，而整段实测是 86.4% 对 56.2%。
  2. 统计窗口显式分段：起播段 / 稳态段 / 每次 seek 后 2 秒各自成段， 不许混算——seek 后的追帧会污染稳态读数。
  3. n < 30 的分位数发 --，与 native 侧 VEPerfHistogram::kMinSamples 一致。两边阈值不同会让同一份数据 在面板和报告里一个有数一个没数。
  4. 泄漏判据样本 < 600 秒判 INCONCLUSIVE。 实证：5 分钟样本测得 RSS +41.6 MB/小时，30 分钟测得 +3.6，相差 11 倍—— 短样本的斜率会被区间内的正常波动主导。
  5. 哨兵值（-1 / -9999）统计前剔除并记录剔除数： 它们是"没测到"，混进均值会把结果拉成负数而看起来像个真实读数。
  6. 指纹缺任何一项 → 拒绝出报告，而不是留空。 留空的报告会被当成"这项不适用"，而实际是"没采到"。

04回归层：跨轮次对照

报告只能回答"这一次跑得怎么样"，答不了"比上次好还是坏"——而后者才是回归测试的核心。 compare-reports.py 补上这一环，判据翻转时退出码非零，可直接接 CI。

拒绝无意义的比较

指纹 asset / software / device 不一致即拒比。 包括"同素材但注入参数不同"——限速下的读数拿去跟不限速对照， 会产出一份看起来像回归报告、实际毫无意义的东西。

阈值按列分别定

各列正常波动差一个数量级：CPU 单次运行方差 30 个百分点，而 fps 稳定在 ±1。 阈值宽于正常波动才不会天天报假警——一旦开始忽略告警， 这个工具就等于不存在。

两个维度值得单独说

故障注入 — 编译期隔离

三个注入点：failHwCreate / failHwConfigure / failHwAfterFrames。最后一条最难触发也最该测——建链期失败还有工厂兜底， 运行期要求播放中途重建软解且画面不中断。

Release 构建里连代码都不存在（实测：注入构建 apk 内相关字符串 3 处，默认构建 0 处）。播放器的故障注入一旦能在生产包里被打开， 就是一个可被利用的稳定性开关。未编入该能力的构建下，接口返回 -1 并明确告警"设了但不会生效"——否则用例会以为注入成功而实际什么都没注入。

A/V 外部真值 — 唯一不依赖播放器内部状态的判据

此前所有同步判据都是播放器自报：syncWorstMs 取自 "视频 pts 减媒体时钟"，两个内部量相减——时钟本身偏了它也会自洽地 显示同步良好。

做法是素材每帧顶部 8 个黑白色块二进制编码帧号，截屏解色带即得屏幕上真实显示 的是第几帧。色带比烧录数字更可靠——只判像素亮暗，不受字体渲染与压缩伪影影响。 实测累计漂移 −41 ~ +13 ms，均小于半帧（40ms）。

06五种假 PASS

这一节是整套系统里最贵的经验。每一种都真实发生过， 而且当时的输出看起来一切正常。 它们的共同点是：不是数字算错了，是测试根本没测到它声称在测的东西。

  1. 没施加压力。seek 风暴用 harness 的默认步距（3 秒）， 12 个 seek 点被拉长到 36 秒，每次都从容完成——seek=7 abort=0， 压力根本没施加却报 PASS。改用 UI 拖进度条后更糟：seek=0， SeekBar 在 adb input 下不响应。
    对策：每个压力场景定义一个活动量信号，低于阈值判 FAIL 并注明 "PASS 无意义"。
  2. 信号来自别处。锁屏场景报"surface 变化 36 次"， 看起来压力充足——实际本应用只占 5 次，其余来自系统媒体组件 （TBLExoPlayer 等锁屏时也在调 setSurface）。
    对策：logcat 是全局的，压力自检必须按进程过滤。
  3. 素材被系统清理。本机素材放在 /tmp， 被系统清理后 ffprobe 拿不到指纹，生成器按口径正确地拒绝出报告—— 但根因藏得极深，表现却像工具坏了。
    对策：素材迁到工程内目录。
  4. 参数被 shell 吞掉。& 在 adb shell 里被当作后台运行符，URL query ?kbps=2000&stall=6@0.25 只剩 kbps=2000， 断流注入静默丢失。连续三次"stall 场景什么都没测到"都源于此。
    对策：整条命令加引号；服务器日志第一行就记着播放器请求的完整 URL， 那是现成的证据。
  5. 测试本身没跑完。echo "$LIST" | while read 循环体里的 adb 吃掉标准输入，第一轮后 read 读不到东西、 循环静默结束——11 个格式素材只跑了 1 个，输出却显示 PASS。
    对策：先读进数组，循环体不依赖 stdin。
还有一种相邻形态：测量工具污染被测对象。 宿主机流式 adb logcat > file & 与 adb reverse 抢同一条 USB 通道，把 fps 从 23.9 压到 1.4。而且伪装得极好——数据完整、 内存斜率正常，只有 fps 露馅。若只看内存就下"无泄漏"结论， 得到的会是"在错误运行状态下测出的正确数字"。

09素材选用规则

性能对照
只能用四个基线素材（base-h264-1080p / base-hevc-1080p / high-4k / high-fps）， 且必须 60 秒以上——10 秒素材扣掉起播与 seek 窗口后稳态凑不满 30 样本，分位数全是 --。
行为素材
无音轨 / 纯音频 / 不等长 / VFR / 竖屏 / 双音轨，不得用于性能基线，跨素材数字不可比。
VFR 标记
manifest 里标 is_vfr，因为"fps ≈ r_frame_rate"这类判据会在它们身上 稳定误报。判据必须读实测值：90000/3001 只是时基写法，算出来 29.99 恒定，不是 VFR。
缓存排空
manifest 记 cache_drain_sec = 32MB ÷ 码率。低码率素材上缓存能撑 2~12 分钟——不限速时断流 5 秒播放器根本察觉不到， stall 类场景必须叠加限速。

10尚未覆盖

维度阻塞点
运行期硬解 fallback 的完整验证受 MediaCodec surface 平台限制，需改架构（输出到 SurfaceTexture）

为什么"变速/切轨"被推迟而不是硬做： 它们要报的量目前没有任何采集点。现在做只能产出一段没有数字的章节—— 那正是这个项目反复栽跟头的形态：字段名承诺 A、实际给不出 B。 推迟不是砍掉，解除条件很明确：先在变速/切轨路径上加打点（可复用 VESeekTrace 的三阶段模式），有了数再谈报告。

11贯穿全系统的一条原则

这套系统在建设过程中，基于"读代码推断"的判断被实测推翻了二十余次， 其中一个缺陷排查了十三个环节、误判十二次。有效的动作始终只有三个： 打印实际对象地址、打印实际执行分支、把错误码翻成常量名。

所以这套系统最有价值的部分不是任何单个工具，而是把判断权从推理交给了机制：

口径写死进生成器

同一份采集反复喂，只能得出同一组数字。

指纹不符自动拒比

跨素材、跨注入参数的比较根本发不出来。

覆盖率自校验常驻

分段之和与总量对账，漏账当场暴露。

压力自检拦假 PASS

活动量不足即判 FAIL 并注明"PASS 无意义"。

注入编译期隔离

生产包里代码不存在，不靠运行时开关。

容差按物理量推导

按分辨率与耗时算，独立误差平方和合成，不拍脑袋。

这些机制在建设期就反复证明了自己：覆盖率自校验上线当天逮住第八次指标错误， 压力自检抓到两次假 PASS，进程过滤揪出第三种假 PASS 形态。 规则靠人执行防不住——包括防写下规则的人。
